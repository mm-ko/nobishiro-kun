## 時間と料金の測定方法

- `time.perf_counter()` で各サービス関数の開始から完了までを測定した。
- httpxのrequest/responseフックで、HTTP送信から本文の受信完了までの秒数・ステータス・Provider・`usage` の数値だけを収集した。
- 料金は各応答の `usage.cost` を合算した。トークン数に公開単価を掛けた見積もりではない。費用が取得できない場合は不明とし、0として補完しない。
- 単元推定とパターン分析はStage B内部の別々のAPI呼び出し。対象内のケースでは、1テストにつきStage A 1回、Stage B 2回、コメント1回の計4回を使用した。
- 人が確認・修正する時間、画像選択・アップロード、ブラウザ通信、認証、DB保存、Docker起動、計測準備は合計時間に含めない。

OpenRouterは非ストリーミング応答に利用情報を含め、`usage.cost` をアカウントに請求する額として説明している。APIの金額の基準通貨は米ドル。[利用情報の公式仕様](https://openrouter.ai/docs/cookbook/administration/usage-accounting)、[通貨・請求の公式説明](https://openrouter.ai/docs/faq#credit-and-billing-systems)

## タイムアウトの推奨値

以下は5問に切り取った画像の少数試行をもとにした、MVPでは実装しない将来の暫定案で、設定変更は行っていない。

| 対象 | 推奨値 | 根拠・制約 |
| --- | --- | --- |
| OpenRouterへの1回のHTTP呼び出し | 計測環境と同じ60秒を将来の検討候補とする | 今回の切り取り画像の検証では最大20.061秒だったが、テスト用紙全体の測定を含めた追加検証が必要。コードの初期値30秒は変更しない |
| BackendのStage A / Stage B各リクエスト全体 | 100秒の総処理期限を設ける案 | フロントの120秒より短くし、通信・エラー通知の余裕を確保する。Stage Bはコメントを含む。未実装 |
| Frontendの待ち時間 | 現在の120秒を維持する案 | 今回は各段階とも範囲内。ただしBackend総処理期限の導入とセットで再検証する |

コードの未設定時の初期値は `openrouter.py` の `DEFAULT_TIMEOUT_SECONDS = 30`。`backend/.env.example` の `OPENROUTER_TIMEOUT_SECONDS` は空欄であり、60秒はリポジトリ共通の初期値ではない。今回の60秒は、手元の計測用Dockerコンテナに設定されていたプロセス環境変数を `settings.openrouter_timeout_seconds` 経由で取得した値で、envファイル自体は参照していない。

この60秒はhttpxのタイムアウト設定であり、アプリの総処理期限ではない。httpxのタイムアウトは接続・読み取り等の待ち時間に適用され、厳密な総経過時間の上限とも異なる。[httpx公式仕様](https://www.python-httpx.org/advanced/timeouts/)

通信の最大3試行に加え、出力のJSON・スキーマ検証にも再試行がある。Stage Bは単元推定・パターン分析・コメントの複数呼び出しを行うため、現状のままでは120秒以内の完了は保証できない。総処理期限を導入する際は、残り時間に応じて呼び出しと再試行を制御する必要がある。今回はその挙動の実装・障害注入試験を行っていない。

画像2枚時や混雑時は未測定のため、今回の推奨値をそのまま確定値にしない。

現行の `backend/app/features/usage/service.py` の `check_rate_limit` と `cache.py` は未実装の入口であり、推奨値がすでに適用済みという意味ではない。実装は関連Issueで扱う。
