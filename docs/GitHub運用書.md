# GitHub運用書

---

## 1. ブランチ運用

### 1-1. 基本ルール

- **`main` / `develop` へ直接pushしない。** 必ずブランチを切ってPR経由でマージする。
  - ※例外：ドキュメント（`docs/`配下の`.md`）と、PRテンプレート（`.github/pull_request_template.md`）は、当面`develop`で直接編集してよい。コード（`backend/`・`frontend/`など）は、必ずブランチを切ってPR経由でマージする。
- **`develop`**：開発・テスト環境用の統合ブランチ。日々の開発はここに集約する。
- **`main`**：リリース用ブランチ。
- 作業ブランチは`develop`に対してPRを作成しマージする。
- リリースするタイミングで`develop`→`main`へPRを作成しマージする。

### 1-2. ブランチ名の形式

```
<接頭辞>/<Issue番号>-<内容>
```

例：`feature/15-login-page` / `docs/25-create-readme`

### 1-3. ブランチ種別（接頭辞）

| 接頭辞 | 用途 |
| --- | --- |
| `feature/` | 機能追加 |
| `fix/` | バグ修正 |
| `docs/` | ドキュメント |
| `refactor/` | リファクタリング |
| `chore/` | Docker・環境設定など |

### 1-4. 作業を始める前に（必須）

新しい作業を始める前は、必ず以下を実行し、ローカルの`develop`を最新にしてからブランチを切る。

```bash
git checkout develop
git pull origin develop
git checkout -b feature/15-login-page
```

古い`develop`から作業ブランチを切ると、後から余計なコンフリクトの原因になるため、**このコマンドを打つことを、作業開始のたびの習慣にする。**

## 2. Issue運用

### 2-1. 進め方（2段階）

1. **現段階（画面設計・API設計・DB設計が固まる前）**：MVPの内容から、必要な作業を大きな粒度で洗い出し、Issue化する。
2. **画面設計・API設計・DB設計が固まった段階**：**1 Issue＝1タスク**の粒度へ分割・修正する。大きい作業は分割して複数Issueにする。

### 2-2. 運用ルール

- Issueには「何を・なぜ・完了条件」を書く（詳細は2-3のテンプレート参照）。
- 着手する人はIssueを自分に**アサイン（担当者設定）**する（作業の重複防止）。
- ブランチ名・PRにIssue番号を紐づける（例：`feature/15-login-page`のブランチで、PRに`refs #15`と記載。完了条件をすべて満たす最後のPRだけ`close #15`にする。詳細は3章の「関連Issueの書き方とIssueの閉じ方」を参照）。

### 2-3. Issueテンプレート

Issue作成時は、以下の項目を（必要に応じて）記載する。GitHubの「Issue templates」機能を使い、テンプレート化しておくと記入漏れを防げる。

```markdown
## 作業内容


## 完了条件


## 担当者（Assignee）


## 関連するIssue（依存関係）


## 前提となるIssue

```

### 2-4. Issue作成後のレビュー手順

1. Issueを作成し、担当者（分かれば）をアサインする。
2. カンバンボードの「Todo」列に追加する。
3. チームのチャットで「Issueを作成しました、確認をお願いします」と一言アナウンスする（個別のIssueリンクをまとめて共有すると見やすい）。
4. レビュー期限は**即日、遅くとも翌日まで**とする。
5. レビューは以下のルールで統一する。
   - 懸念・抜け漏れがあれば、該当Issueにコメントする。
   - 問題なければ、リアクション（いいねスタンプ等）で承認を示す。
6. コメントがついたIssueは、内容を修正し、再度確認を依頼する。
7. 期限までに大きな懸念が出なければ、そのまま「Todo」に残し、着手可能な状態とする。

## 3. Pull Request（PR）運用

- **PRは小さく。** 1PRで扱う変更は1タスク分に留める（レビューしやすさ最優先。目安：数百行を超える一括変更はしない）。
- **コミットする前に、必ず差分を確認する。**
  AIエージェントに実装を依頼した場合も、コミット・pushはエージェントに一任せず、必ず人が差分を確認してから行う。
  - `git status` で、変更されたファイルの一覧を確認する。
  - `git diff` で、変更の中身を確認する（意図しないファイル・行が含まれていないか）。
  - `git add` 済みの内容をもう一度確認したい場合は `git diff --staged` を使う。
- **PRを作成する前に、必ずGitHub上でFiles changedを確認する。**
  ローカルでAIエージェントとだけ対話して作業を進めていると、意図しないファイル（developで別のメンバーが更新した、無関係なファイルなど）が差分に紛れ込んでいても気づけないことがある。ローカルの確認だけで終わらせず、GitHub上でも実際の差分をあらためて確認してからPRを作成する。特に、次の2点は必ず見る。
  - Files changed に、意図しないファイルが含まれていないか。
  - Behind（developからどれだけ遅れているか）が大きくなっていないか（1-4の習慣＝作業開始前にdevelopをpullすることを忘れていないか）。
- **レビューを受けてから必ずmergeする。** 無レビューでのマージは禁止。レビューは次のいずれかで実施する。
  - **他メンバーによるレビュー**（最低1名のApprove）
  - **AIレビュー**を実施し、指摘に対応する。**AIレビューを行う際は、コードだけでなく、対象PRに関連するIssue（作業内容・完了条件）も必ず読み込ませた上でレビューさせること。**（詳細はセクション9「AIエージェント利用のルール」参照）
- レビュー指摘は会話で解決し、`Resolve conversation`してからマージ。
- マージ後は作業ブランチを削除する。
- CI（テスト）が通っていることを確認してからmerge。

※ドキュメント（`.md`）のレビューは、上記より軽いルール（懸念があればコメント、問題なければリアクション）で運用する（2-4参照）。コード変更を伴うPRは、このセクション3のルールに従う。

### 関連Issueの書き方とIssueの閉じ方

- PR本文の「関連Issue」は、テンプレートの初期値 `refs #番号` のまま出す。
- Issueの一部だけを実装するPR（デモ向けの部分実装など）は `refs #番号` とする。マージしても、Issueは閉じない。
- 完了条件をすべて満たす**最後のPR**だけ、`refs` を `close` に変える。マージ時にIssueが閉じ、カンバンもDoneに移る。変え忘れた場合は、マージ後にIssueを手で閉じる。
- コミットメッセージには `fix`・`close` を書かず、番号だけ書く（書くとマージ時にIssueが閉じることがある）。
- 誤ってIssueが閉じた場合は、Issueのページの「Reopen issue」で開き直す。

### 部分実装のPRをマージしたあと（Issueを残すとき）

- 済んだ項目にだけチェックを入れ、残りは未チェックのままにする。
- Issueにコメントを残す。例：「UI-006の表示と操作を実装（PR #〇〇）。残りは、#32とのつなぎ、本物のAPIへの置き換え」
- カンバンは「In Progress」のままにする（Doneは、Issueを閉じたときに自動で移る）。

## 4. コンフリクトが起きたら

- コンフリクトは慌てず、どちらの変更を残すか**内容を理解してから**解消する（作業開始前に`develop`を最新にする手順は1-4を参照）。
- **一人で解決が難しい場合は、抱え込まず早めにチームに共有すること。**
- 解消後は必ず動作確認・テストをしてからコミット・push する。

## 5. PRテンプレート

PRを作成すると、以下のテンプレートが自動で入るようにする（`.github/pull_request_template.md`に配置）。

```markdown
## 目的

<!-- なぜこの変更をするのか。関連する背景 -->

## 変更内容

<!-- 何を変えたか。箇条書きで -->

## 確認方法

<!-- レビュアーが動作確認する手順 -->

1.

## 画面差分

<!-- UI変更がある場合はスクリーンショットを貼る。無ければ「なし」 -->

## 関連Issue
refs #

<!-- 書き方
 ・Issueの一部だけを実装するPR：refs #番号（Issueは閉じない）
 ・完了条件をすべて満たす最後のPR：refs を close に変える（マージ時にIssueが閉じる）
 ※ コミットメッセージには fix や close を書かない（番号だけ書く）
-->
```

## 6. コミットメッセージ

- 1コミット＝意味のある単位。

  ```
  feat:     引き継ぎ入力フォームを追加
  fix:      ログイン時のトークン検証を修正
  docs:     READMEにER図を追加
  style:    整形・インデントなど（動作に影響しない変更）
  refactor: 挙動を変えずに内部構造を整理
  test:     テストの追加・修正
  ```

---

## 7. レビューの心得

- **早く・小さく出す**（大きなPRはレビュー待ちの原因）。
- 指摘は「人」ではなく「コード」に対して。具体的・建設的に。
- 分からない点は質問でOK。承認を急がない／急かさない。

---

## 8. やってはいけないこと（NG集）

- ❌ `main` / `develop`への直接push／直接コミット（`docs/`配下のドキュメントとPRテンプレートは当面例外。1-1参照）
- ❌ レビューなしのマージ（他メンバー or AIレビューのどちらも通していない状態でのマージ）
- ❌ 巨大PR（数百行超の一括変更）
- ❌ 複数タスクを1つのPR・Issueに詰め込む
- ❌ `.env`など秘密情報のコミット（`.gitignore`で除外）

## 9. AIエージェント利用のルール

エージェントの基本的な行動ルール（破壊的操作の禁止、設計→承認→実装の流れ、変更範囲の限定、秘密情報の扱いなど）は`CLAUDE.md`/`AGENTS.md`に集約する。ここでは、それ以外のプロジェクト固有のルールのみ記載する。

### 9-1. コーディング規約の遵守

- どのエージェントを使っても、作業対象のBackend／Frontendコーディング規約に沿ったコードになるよう、エージェントへの指示に規約を含める。

### 9-2. 生成コードのレビュー基準

- AIが生成したコードも、人が書いたコードと同じ基準でレビューする。セクション3の「AIレビュー」を実施する場合も、**対象の作業内容が分かるIssueを読み込ませた上で**レビューさせ、指摘への対応・`Resolve conversation`を経てからマージする。

### 9-3. 実装を依頼する前に、必ず読み込ませるドキュメント

実装をエージェントに依頼する際は、以下を最低限読み込ませた上で指示すること。

**必須（すべてのAIエージェントで、常に）**
- [ ] `CLAUDE.md`（Claude Codeを使う場合）
- [ ] `AGENTS.md`（Codexを使う場合）
- [ ] GitHub運用書
- [ ] PRD（最新版）
- [ ] 技術選定.md
- [ ] 作業対象のBackend／Frontendコーディング規約

**推奨（該当する場合）**
- [ ] API設計.md
- [ ] DB設計.md
- [ ] 画面設計.md（ワイヤーフレーム）
- [ ] セキュリティ設計.md

※`CLAUDE.md`・`AGENTS.md`は、リポジトリ直下に配置し、破壊的操作の禁止・作業の進め方（設計→承認→実装）・変更範囲の限定・コミット規約・報告の作法など、エージェント利用の基本ルールを定めたもの。**使用するエージェントに関わらず、必ず最初に読み込ませること。** 各リポジトリで「8. プロジェクト情報」（プロジェクト名・技術スタック・ディレクトリ構成・独自ルール）を記入し、内容を最新に保つこと。

※ドキュメント量が多い場合、PRD・技術選定.mdの「決定事項」だけを抜き出した要約を別途用意すると、エージェントが読み取りやすくなる（時間に余裕があれば検討）。

## 10. フォルダ・ファイル命名規則

- ドキュメント（`.md`）は、日本語名（例：`技術選定.md`）で統一する。
- PRDのように複数バージョンが存在するファイルは、`PRD_Ver_1_XX.md`の形式を維持する。
- 過去のバージョン・古いドキュメントは`docs/archive/`に移動する。

## 11. MUSTドキュメントの方針（決定事項）

- **コーディング規約**：MUST項目。Backend・Frontendでそれぞれ担当分を執筆し、読みやすさと更新のしやすさを優先して別ファイルで管理する。参照先は[Backendコーディング規約](<バックエンド_コーディング規約 v2.md>)と[Frontendコーディング規約](フロントエンドコーディング規約.md)とする。
- **シーケンス図**：今回は作成しないことに決定。アーキテクチャ図と技術選定.md内の処理フロー（AI分析イメージ）の説明で代替可能と判断したため。
- ドキュメント全体の担当・進め方は`PRD`および`技術選定.md`の更新履歴を参照。

## 12. カンバンボード（GitHub Projects）の運用

- Issueを作成したら、カンバンボードに追加する。
- 列構成（例）：Todo / In Progress / Done
- Sprintごとに列を分ける場合は、Sprint名で列を作る運用も検討可。

### 12-1. ステータス更新の自動化

担当者が手動で列を移動させる運用ではなく、**GitHub Projectsの組み込みワークフロー（Built-in workflows）**を使って自動化する。

**設定方法**：対象のProjectを開き、右上の「⋯」メニューから「Workflows」を選択し、以下を設定する。

| タイミング | 自動で移動する列 |
|---|---|
| Issue／PRがプロジェクトに追加されたとき | Todo |
| Issueがクローズされたとき（PRのマージでIssueが自動クローズされた場合を含む） | Done |

より細かく「PRを作成したらIn Progressへ移動する」という制御をしたい場合は、GitHub Actions（GraphQL API経由）でのカスタムワークフローが必要になる（組み込みワークフローだけでは対応できない）。まずは組み込みワークフローで最低限の自動化（追加時→Todo、クローズ時→Done）を行い、必要であれば後から拡張する。

🔵 「In Progress」への移動を自動化するか（Issueへのアサイン時／紐づくPRのopen時など、どのタイミングで移動させるか）は、チームで運用しながら決める。
