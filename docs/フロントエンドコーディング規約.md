# のびしろくん Frontend コーディング規約

> 対象：小学3年生 算数学習トラッキングアプリ「のびしろくん」  
> Frontend：Next.js + TypeScript  
> 画面：スマートフォン利用を前提  
> 基準：PRD / 画面設計書 / API仕様書 / Frontend環境構築Issue / GitHub運用書  
> 目的：Frontend担当者が並行開発するときの品質統一・責務分離・Gitコンフリクト低減

---

## 1. この規約の目的

本規約は、コードの書き方だけでなく、複数人で安全にフロントエンド開発を進めるための共通ルールを定める。

特に以下を重視する。

- 誰が書いても読みやすいコードにする
- Issueごとの担当範囲を明確にする
- 同じファイルを複数人が同時に編集する状況を減らす
- 画面・API通信・状態管理の責務を混ぜない
- BackendとのAPI仕様を統一する
- スマートフォンで使いやすい画面を作る
- テスト画像や個人情報を安全に扱う

迷った場合は、次の順で確認する。

1. PRD・画面設計書
2. API仕様書
3. 本コーディング規約
4. 既存コード
5. チームで相談

---

## 2. 技術スタックと決定事項

Frontendは以下を基本とする。

- Node.js 22 LTS
- Next.js
- TypeScript
- App Router
- CSS Modules
- React Context
- Vitest
- React Testing Library
- スマートフォンファースト

チームで決定済みの方針は次のとおりとする。

| 項目 | 方針 |
|---|---|
| CSSの書き方 | CSS Modules |
| ログイン状態の管理 | React Context＋`frontend/lib/auth.ts` |
| フロントのテスト | Vitest＋React Testing Library |
| Node.js | 22 LTS |
| ディレクトリ構成 | `src/`なし |

Tailwind CSS、Jest、Zustandは初期構築では使用しない。

## 3. ディレクトリ構成

本プロジェクトでは`src/`ディレクトリを使用しない。

画面は`frontend/app/`配下に作成し、機能固有のコードは`frontend/features/`配下に配置する。

基本構成は次のとおりとする。

```text
frontend/
├─ app/
├─ components/
├─ features/
├─ hooks/
├─ lib/
│  └─ auth.ts
├─ types/
├─ public/
├─ package.json
└─ vitest.config.ts
```

各ディレクトリの役割は次のとおりとする。

- `app/`：App Routerのページ、レイアウト、ルーティング
- `features/`：特定の機能に属するComponent、Hook、API通信、型
- `components/`：複数の機能で共通して使用するComponent
- `hooks/`：複数の機能で共通して使用するHook
- `lib/`：複数の機能で共通して使用する処理や外部サービスの初期化
- `types/`：複数の機能で共通して使用する型
- `public/`：公開する静的ファイル

必要になっていないディレクトリを、構成をそろえる目的だけで作成しない。

実際のディレクトリ構成は、Frontend環境構築Issueで確定した構成を正とする。

## 4. Issueを基準に実装する

実装はGitHub Issueを作業単位とする。

Frontend関連の主なIssueは次のとおりとする。

- [2-03] 画面遷移図・ワイヤーフレームの確定
- [2-05] GitHub運用書に沿った設定の反映
- [3-07] 認証画面（新規登録・ログイン・ログアウト）
- [3-08] テスト画像のアップロード・トリミング
- [4-04] AI読み取り内容の確認・修正と得点・満点の入力
- [4-05] 分析結果画面
- [5-03] 学習履歴一覧の表示
- [5-05] ホーム画面・苦手単元ランキング表示
- [6-02] Frontend単体テストの整備（Vitest）
- [6-03] 結合確認・AI回帰確認・バグ修正
- [4-08] CI（GitHub Actions）：Lint・テストの自動実行

Issueの範囲を超える変更を独自判断で追加しない。

## 5. 基本方針

### 5-1. シンプルさを優先する

MVPでは過度な抽象化を避ける。

- 将来使うかもしれないという理由だけで共通化しない
- 1回しか使用しない処理を無理に共通化しない
- 実際に複数箇所で必要になった時点で共通化する
- 初学者でも処理を追える構成を優先する

### 5-2. 機能単位でコードをまとめる

特定の機能でのみ使用するコードは、その機能のディレクトリ内に配置する。

```text
frontend/
└─ features/
   ├─ auth/
   │  ├─ components/
   │  ├─ contexts/
   │  ├─ hooks/
   │  ├─ api/
   │  └─ types/
   ├─ test-analysis/
   │  ├─ components/
   │  ├─ hooks/
   │  ├─ api/
   │  └─ types/
   ├─ learning-history/
   ├─ ranking/
   └─ payment/
```

配置の判断基準は次のとおりとする。

- 特定の機能でのみ使用するもの  
  → `frontend/features/<feature名>/`配下
- 複数の機能で共通して使用するもの  
  → `frontend/components/`、`frontend/hooks/`、`frontend/lib/`、`frontend/types/`

例えば、テスト分析機能でのみ使用するHookは次の場所に配置する。

```text
frontend/features/test-analysis/hooks/
```

複数の機能で共通して使用するHookは次の場所に配置する。

```text
frontend/hooks/
```

同じ機能に属する複数の画面で使用する場合は、機能固有として扱い、`features/<feature名>/`配下に置く。

最初から`common/`や`shared/`といったディレクトリは作成しない。

## 6. App Router

Next.jsのApp Routerを使用する。

```text
frontend/
└─ app/
   ├─ login/
   │  └─ page.tsx
   ├─ home/
   │  └─ page.tsx
   ├─ test-upload/
   │  └─ page.tsx
   ├─ review/
   │  └─ page.tsx
   └─ result/
      └─ page.tsx
```

Next.jsの特殊ファイル名は標準に従う。

- `page.tsx`
- `layout.tsx`
- `loading.tsx`
- `error.tsx`

Pages RouterとApp Routerを理由なく混在させない。

---

## 7. Server Component / Client Component

App RouterではServer Componentを基本とする。

以下のようなブラウザ上の処理が必要な場合のみ、Client Componentを使用する。

- `useState`
- `useEffect`
- `useContext`
- `onClick`などのイベント処理
- 入力フォーム
- 画像選択
- 画像プレビュー
- 画像トリミング
- ブラウザ上の状態管理
- Firebase Authenticationの認証状態監視

Client Componentには、ファイルの先頭に次の記述を追加する。

```tsx
"use client";
```

必要のないComponentに`"use client"`を付けない。

画面全体をClient Componentにするのではなく、ブラウザ上の処理が必要な範囲に限定する。

## 8. 命名規則

### Component

PascalCaseを使用する。

```text
TestUpload.tsx
AnalysisResult.tsx
ScoreInput.tsx
```

### 変数・関数

camelCaseを使用する。

```text
testImage
analysisResult
confirmedAnswers
```

### Boolean

状態が分かる名前にする。

```text
isLoading
isAnalyzing
hasError
canSubmit
isConfirmed
```

`flag`、`check`、`tmp`、`data2`などの曖昧な名前を避ける。

### イベント処理

イベント関数は`handle`から始める。

```text
handleLogin
handleUpload
handleSubmit
handleNext
handleCorrection
```

### 型

型・interfaceはPascalCaseを使用する。

```text
AnalysisResult
StageAResponse
ConfirmedAnswer
```

### 定数

変更しない定数はUPPER_SNAKE_CASEを使用する。

```text
MAX_UPLOAD_IMAGES
MAX_FILE_SIZE
```

## 9. TypeScript

原則として`.ts`または`.tsx`を使用する。

`any`の使用は原則避ける。

悪い例：

```ts
const result: any = data;
```

良い例：

```ts
type AnalysisResult = {
  score: number;
  comment: string;
};
```

APIのRequestとResponseには型を定義する。

API仕様書で決められた項目名・型を正とし、Frontend側だけで独自の項目名へ変更しない。

---

## 10. Componentの責務と配置

1つのComponentに複数の大きな役割を詰め込まない。

`page.tsx`は画面全体の構成を担当し、細かいUIや処理はComponentへ分離する。

次の例は、`page.tsx`が各Componentを組み合わせて画面を構成することを表している。

```text
page.tsx
├─ UploadArea
├─ ImagePreview
├─ ScoreInput
└─ PrimaryButton
```

これは、ファイルをすべて`page.tsx`と同じディレクトリに置くという意味ではない。

実際の配置例は次のとおりとする。

```text
frontend/
├─ app/
│  └─ test-upload/
│     └─ page.tsx
│
├─ features/
│  └─ test-upload/
│     └─ components/
│        ├─ UploadArea.tsx
│        ├─ ImagePreview.tsx
│        └─ ScoreInput.tsx
│
└─ components/
   └─ PrimaryButton.tsx
```

- `UploadArea`、`ImagePreview`、`ScoreInput`  
  → テストアップロード機能でのみ使用するため、`features/test-upload/components/`に配置する
- `PrimaryButton`  
  → 複数機能で共通して使用するため、`components/`に配置する

ただし、細かく分割しすぎて処理を追いにくくしない。

---

## 11. 共通Component

複数の機能で実際に使用するUIのみ、共通Componentとする。

共通Componentは次の場所に配置する。

```text
frontend/components/
```

特定の機能でのみ使用するComponentは次の場所に配置する。

```text
frontend/features/<feature名>/components/
```

共通Componentの例は次のとおりとする。

- Button
- Card
- Modal
- Loading
- ProgressBar

同じComponentが複数画面で使われていても、それらの画面が同じ機能に属する場合は、機能固有Componentとして扱う。

複数の機能で必要になった時点で、`frontend/components/`への移動を検討する。

`common/`や`shared/`といった別の共通ディレクトリは作成しない。

---

## 12. API通信

APIのURL・Request・ResponseはAPI仕様書を正とする。

Component内にAPI通信処理を大量に直接記述しない。

機能ごとのAPI処理へ分離する。

```text
frontend/
└─ features/
   └─ test-analysis/
      └─ api/
         └─ analyzeTest.ts
```

複数の機能で共通して使用するAPIクライアントや共通処理は、`frontend/lib/`への配置を検討する。

Frontend側でBackendの処理を推測して、独自のAPI仕様を作らない。

---

## 13. 認証

認証にはFirebase Authenticationを使用する。

Firebase Authenticationの初期化処理と、ログイン・新規登録・ログアウトなどの共通処理は、次のファイルに配置する。

```text
frontend/
└─ lib/
   └─ auth.ts
```

`lib/auth.ts`には、主に以下を配置する。

- Firebase Authenticationの初期化
- ログイン処理
- 新規登録処理
- ログアウト処理
- 認証に関する共通処理

ログイン状態の共有にはReact Contextを使用する。

React Contextでは、主に以下の状態を管理する。

- 現在ログインしているユーザー
- 認証状態を確認中かどうか
- ログイン済みかどうか

Context、Provider、Hookは認証機能に属するコードとして配置する。

```text
frontend/
├─ lib/
│  └─ auth.ts
│
└─ features/
   └─ auth/
      ├─ contexts/
      │  └─ AuthContext.tsx
      ├─ components/
      │  └─ AuthProvider.tsx
      ├─ hooks/
      │  └─ useAuth.ts
      └─ types/
```

`AuthProvider`は、必要な範囲に応じて`frontend/app/layout.tsx`などで使用する。

初期構築では、ログイン状態の管理を目的としてZustandなどの追加の状態管理ライブラリを導入しない。

Backendへ認証が必要なRequestを送る場合は、Firebaseの認証トークンを送信する。

ログイン中ユーザーの`user_id`を、FrontendからRequest bodyやQueryへ独自に追加しない。

ユーザーの特定は、Backend側のFirebaseトークン検証結果に任せる。

トークンや認証情報を`console.log`へ出力しない。

認証トークンをFrontend側で独自に`localStorage`へ保存しない。

---

## 14. 状態管理

Component内で完結する状態は`useState`などを使用する。

複数のComponentで状態を共有する必要がある場合は、必要な範囲に限定してReact Contextを使用する。

ログイン状態は、Firebase AuthenticationとReact Contextを組み合わせて管理する。

Stage Aから保護者確認までの途中データはFrontend側で保持する必要があるが、個人情報や画像を不要に永続保存しない。

状態は可能な限り、その状態を使用するComponentに近い場所で管理する。

すべての状態を1つのContextへまとめない。

初期構築ではZustandを導入しない。React Contextでは管理が難しい状態が発生した場合に、チームで導入を検討する。

---

## 15. Stage A / Stage B

本アプリではAI分析をStage AとStage Bに分ける。

### Stage A

テスト画像から見えている内容を読み取る。

Stage Aの結果は自動確定しない。

### 保護者確認

Stage Aの結果をFrontendで表示し、保護者が内容を確認して、必要に応じて修正する。

得点と満点も保護者が入力する。

### Stage B

保護者が確認したデータをBackendへ送信し、単元推定・間違え方分析を行う。

Stage Bには画像を送らない。

未確認のStage Aの結果を、そのままStage Bへ送らない。

---

## 16. テスト画像

テスト画像は最大2枚（表・裏）までとする。

Frontendでは以下を守る。

- 画像を必要以上に保持しない
- `localStorage`などへ画像を保存しない
- `console.log`に画像内容やbase64を出さない
- 実際の児童のテスト画像をGitへ入れない
- 個人情報を固定のテストデータとして使用しない

画像は分析処理に必要な間だけ扱う。

---

## 17. 読み取り結果確認画面

読み取り結果確認画面では、以下を扱う。

- AI読み取り結果の表示
- 読み取り内容の修正
- 保護者による得点入力
- 保護者による満点入力
- 確認済みデータのStage Bへの送信

Frontend側で、AIの読み取り結果を自動的に正しいものとして確定しない。

---

## 18. 分析結果画面

分析結果はBackendから返されたデータを表示する。

Frontend側で独自に、学習理解度や間違いの原因を推測しない。

文章形式のフィードバックは、Backendから返されたコメントを表示する。

対象外・判定困難などの状態も、API仕様に従って適切に表示する。

---

## 19. ホーム・ランキング・学習履歴

ランキングと学習履歴はBackend APIから取得したデータを表示する。

FrontendでBackendと異なる計算ロジックを作らない。

以下の画面仕様は、関連Issue・画面設計書を正とする。

- 苦手単元ランキング
- 学習履歴一覧
- テスト結果表示

---

## 20. スマートフォン対応

本アプリはスマートフォン利用を前提とする。

モバイルファーストで実装する。

必須事項は次のとおりとする。

- スマートフォン幅で表示崩れがない
- 横スクロールを発生させない
- 文字を小さくしすぎない
- ボタンや入力欄を指で操作しやすいサイズにする
- 画像が画面幅を超えない
- 操作ボタンを分かりやすい位置に配置する

PC表示だけを確認して完了としない。

---

## 21. CSS Modules

スタイルにはCSS Modulesを使用する。

Component固有のスタイルは、対象のComponentと同じディレクトリに配置する。

```text
frontend/
└─ features/
   └─ test-upload/
      └─ components/
         ├─ UploadArea.tsx
         └─ UploadArea.module.css
```

CSS Modulesは次のように読み込む。

```tsx
import styles from "./UploadArea.module.css";
```

```tsx
<div className={styles.uploadArea}>...</div>
```

全画面に適用する必要があるスタイルのみ、`frontend/app/globals.css`に記述する。

`globals.css`で扱うものの例は次のとおりとする。

- CSSリセット
- 基本フォント
- 背景色
- CSSカスタムプロパティによる共通色
- 全画面共通の基本スタイル

画面やComponent固有のスタイルを`globals.css`へ追加しない。

同じ色、余白、角丸などを各画面でバラバラに定義しない。

Tailwind CSSは使用しない。

Tailwind CSSのパッケージ、設定、`@import "tailwindcss"`、Tailwind固有のクラスを残さない。

新しいCSSライブラリを追加する場合は、事前にチームで合意する。

---

## 22. Formatter / Linter

FormatterとLinterは、Frontend環境構築IssueおよびCI設定を正とする。

CIでLintとテストを自動実行する。

新しいFormatterやLinterを個人判断で追加しない。

ESLintやPrettierを採用する場合は、リポジトリ側にチーム共通設定を置く。

VS Codeの個人設定だけに依存しない。

---

## 23. console / Logging

不要な`console.log`を残さない。

特に以下を出力しない。

- Firebase token
- Password
- API Key
- 個人情報
- テスト画像
- base64画像
- AIの入出力全文

Frontendのエラー表示と、開発者向けのログを混同しない。

---

## 24. エラー表示

Backend内部の例外内容を、そのままユーザーへ表示しない。

悪い例：

```text
Internal Server Error: OpenRouter timeout...
```

良い例：

```text
分析に失敗しました。
時間をおいてもう一度お試しください。
```

対象外単元や判定困難など、仕様上の正常な結果と通信エラーを区別する。

---

## 25. アクセシビリティ

最低限、以下を守る。

- 画像には適切な`alt`を付ける
- クリック操作には`button`を使用する
- 入力欄には`label`を付ける
- 色だけで正解・不正解などを表現しない
- キーボード操作でも利用可能な構造を意識する

---

## 26. 依存ライブラリ

新しいライブラリを追加する場合はチームへ共有する。

以下を確認する。

- 本当に必要か
- 既存ライブラリで代替できないか
- 同じ目的のライブラリがすでにないか
- 保守性やセキュリティ上の問題がないか

「便利そう」という理由だけで追加しない。

追加理由はPull Requestに記載する。

---

## 27. テスト

Frontendの単体テストにはVitestを使用する。

React ComponentのテストにはReact Testing Libraryを使用する。

「Testing Library」はテスト支援ライブラリ群の総称であり、React Componentのテストでは`@testing-library/react`を使用する。

Jestは使用しない。

テストファイルは、原則としてテスト対象のファイルと同じディレクトリに配置する。

```text
frontend/
└─ features/
   └─ test-upload/
      └─ components/
         ├─ ScoreInput.tsx
         ├─ ScoreInput.module.css
         └─ ScoreInput.test.tsx
```

テストファイル名は次の形式とする。

- TypeScript：`*.test.ts`
- React Component：`*.test.tsx`

テスト名は、何を確認するテストか分かる名前にする。

優先してテストするものは次のとおりとする。

- 入力値チェック
- 得点・満点入力
- ユーザー操作による表示変化
- APIレスポンスによる表示切替
- エラー表示
- Stage A / Stage Bの画面フロー
- ランキング・学習履歴の表示

Componentの内部実装ではなく、ユーザーから見た表示と操作をテストする。

要素の取得には、可能な限りRole、Label、表示文字列など、ユーザーが認識できる情報を使用する。

外部APIやFirebaseへ直接接続する単体テストは避け、必要に応じてモックを使用する。

Jest固有のAPIや設定を追加しない。

## 28. Node.js

Node.jsは22 LTSを使用する。

他のメンバーが同じ環境を再現できるように、Node.jsのバージョンをプロジェクト内で明示する。

`package.json`では、使用するNode.jsのバージョンを`engines`に設定する。

例：

```json
{
  "engines": {
    "node": "22.x"
  }
}
```

必要に応じて`.nvmrc`または`.node-version`を配置する。

READMEにもNode.js 22 LTSを使用することを記載する。

Pull Request作成前に`node -v`を実行し、22系であることを確認する。

## 29. Git / Issue / Pull Request

Gitの詳細運用はGitHub運用書を正とする。

基本ルールは次のとおりとする。

- 1つのIssueに対して1つの目的で作業する
- Issueと関係のない変更をPull Requestへ混ぜない
- 大規模なformat変更を機能Pull Requestに混ぜない
- 他担当者の作業領域を変更する場合は共有する
- `main`や`develop`へ直接コミットしない
- 最新の`develop`から作業ブランチを作成する

ブランチ名やPull Request名は、GitHub運用書で定めた形式を使用する。

---

## 30. Pull Request作成前チェック

Pull Request作成前に、最低限以下を確認する。

- 担当Issueの範囲だけを変更している
- PRD・画面設計書と一致している
- API仕様書とRequest・Responseが一致している
- Node.js 22.xを使用している
- `npm ci`が成功する
- `npm run build`が成功する
- TypeScriptエラーがない
- `npm run lint`が成功する
- `npm run format:check`が成功する
- 必要なVitestのテストが成功している
- 不要な`console.log`がない
- 不要なコメントアウトがない
- `any`を安易に使用していない
- 不要な`"use client"`が付いていない
- APIキーや認証情報を含んでいない
- 実テスト画像や個人情報を含んでいない
- 画像やAI出力全文をログへ出していない
- Stage AとStage Bの責務を混ぜていない
- Stage Bへ画像を送っていない
- スマートフォンで表示崩れがない
- 横スクロールが発生していない
- Tailwind CSSが残っていない
- Jestの設定が混在していない
- 関係のないファイルを変更していない
- 仕様変更がある場合は関連ドキュメントも更新している

## 31. レビュー時の考え方

レビューでは個人の好みより、以下を優先する。

1. バグ・セキュリティ
2. PRD・画面設計・API仕様との不一致
3. 責務分離
4. スマートフォンでの操作性
5. 可読性
6. テスト
7. 本コーディング規約
8. 個人的な書き方の好み

大きな設計変更は、レビューコメントだけで決定せず、チームで共有する。

## 32. 禁止・避けるパターン

- × 1つの`page.tsx`にすべての処理を書く
- × Componentから直接複雑なAPI処理を書く
- × API仕様書にない項目を独自に追加する
- × `user_id`を独自にRequestへ追加する
- × Stage Aの結果を確認せずStage Bへ送る
- × Stage Bへ画像を送る
- × AIの結果をFrontend側で独自に推測・補完する
- × テスト画像を`localStorage`などへ保存する
- × 個人情報・token・画像をconsoleへ出力する
- × APIキーをコードへ書く
- × 実テスト画像をGitへ入れる
- × `any`を安易に使用する
- × 不要な`"use client"`を付ける
- × 巨大な共通Componentやutilsを作る
- × 最初から`common/`や`shared/`を作る
- × Issueと無関係な変更をPull Requestへ混ぜる
- × PC表示だけを確認して完了とする
- × Tailwind CSSとCSS Modulesを混在させる
- × JestとVitestを混在させる
- × 認証トークンを独自に`localStorage`へ保存する
- × 認証情報を`console.log`へ出力する
- × `dangerouslySetInnerHTML`、`innerHTML`、`document.write`、`eval`を使う（文字をHTMLやプログラムとして直接差し込む書き方。Reactの自動エスケープが効かなくなる）
- × AIの出力（コメント・読み取り結果）やAPIから受け取った文字を、HTMLとして画面に差し込む（外から来た文字は、`{comment}`のように、ただの文字として表示する）
- × 外から受け取った文字を、確認せずにリンク（`href`）や画像（`src`）に使う（`javascript:`で始まるURLなど、悪意のある命令を仕込む手口を防ぐ。使う場合は、`https://`で始まるか、アプリ内のパスであることを確認する）
