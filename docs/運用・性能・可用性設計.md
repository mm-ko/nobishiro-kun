# 運用・性能・可用性設計（簡易版）

## 運用

- 起動・設定準備は[ルートREADME](../README.md)を参照。Backend・DB・MemcachedはCompose、FrontendはPCで別起動する。envファイルや鍵をログ・Gitへ出さない。
- 稼働確認は`GET /v1/health`。DBに接続できれば200、できなければ503。AI・Firebase・Stripe・Memcachedの稼働をまとめて確認するAPIではない。
- 障害時は共通エラーの`request_id`、HTTPステータス、エラーコードで調査する。AIの本文や秘密の設定値を追加出力して調べない。
- DBは名前付きvolumeで保持するが、バックアップとは別。定期バックアップ、復元訓練、保存期間、監視・通知先、リリース／ロールバック手順は未整備。
- DBマイグレーションは承認された別作業として実施する。本Issueでは実行しない。障害時にvolume削除やDB初期化を復旧手順にしない。

## 性能

| 項目       | 現状                                                                                                  | 確認・今後の方針                                                                                                 |
| ---------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 画像       | 最大2枚、既定1枚10MiB・合計20MiB。multipart付加分64KiBを含め受信量を制限。メモリ上で処理              | 展開後画像と同時利用によるメモリ増加は未計測。画像容量上限だけで総メモリは保証しない                             |
| AI通信     | HTTPXのtimeout既定30秒。タイムアウト・429・5xxは最大3試行、待機0.25秒→0.5秒                           | 30秒は全分析の上限ではない。画像ごとの読取・単元判定・パターン分析・コメント生成の呼出しと検証再試行が積み重なる |
| AI出力検証 | Stage A・Stage B・コメントは形式不正時にそれぞれ最大1回の検証再試行                                   | 通信再試行と別枠。総呼出回数・所要時間・費用を代表ケースで記録する                                               |
| DB         | `pool_pre_ping=True`、接続timeout 5秒                                                                 | 実PostgreSQLでの同時保存・ロック待ち・検索性能は別途確認                                                         |
| レート制限 | Stage A／Stage Bそれぞれ1ユーザー1分3回。分単位の固定窓、キーのTTLは120秒。接続・操作timeoutは各0.5秒 | 4回目以降は429と次の分までのRetry-After。Memcachedのキー消失・接続不可時は警告を出して分析を継続                 |

性能目標（応答時間・同時利用数・許容エラー率）は未決定。[OpenRouter計測結果](OpenRouter再検証・計測結果.md)の測定条件を確認し、一例の数値をSLAとして扱わない。負荷試験は未実施。

Frontendは各分析の待機を120秒で打ち切り、fetchを中断する（`frontend/lib/analysisWaiting.ts`、`TestUploadFlow.tsx`）。これはBackendの実行時間上限ではなく、ブラウザーの中断後もAI処理やDB保存が続く可能性がある。タイムアウトを「保存されていない」と断定せず、履歴とエラーコードを確認する。同じ分析IDで保存完了後に再送すると現状は409になる。

## 可用性・障害時の扱い

| 障害・状態                   | 現在の挙動／制約                                                                                                                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AIタイムアウト・サービス失敗 | 分析APIは504／503、形式不正は502。保存前に失敗すれば利用実績・分析記録を保存しない                                                                                                 |
| 対象外・単元判定困難         | 正常な分析結果として返す。利用実績・分析記録を保存しない                                                                                                                           |
| 月間上限                     | 日本時間の暦月で無料2回・有料10回（無料分を含む、MONTHLY_ANALYSIS_LIMITの既定値）。Stage A／Stage B開始前と保存直前に判定し、上限超過は403。保存直前はユーザー単位で直列化         |
| 保存失敗                     | 利用実績と分析記録を同じトランザクションで扱う。保存済み分析IDの再送は409で、保存結果の再返却は未対応                                                                              |
| Stripeの契約取得失敗         | Webhookは503、ロックを解放するためrollback。再送に対応し、重複・順不同を考慮する                                                                                                   |
| 重複契約                     | Checkoutをユーザー単位で直列化し、古い未完了Checkoutを失効。Webhookで二重active契約を検出したら後発を解約。解約失敗はrollbackと503で再送に備える。テストモードのため返金は行わない |
| DB停止                       | ヘルスAPIは503。DB依存機能は継続できない。自動フェイルオーバーなし                                                                                                                 |
| Memcached停止                | レート制限をせずに通し、ユーザーIDやキーを含めないWARNINGを記録。DBによる月間利用制限は継続                                                                                        |

ComposeのDBヘルス待機は起動順の制御であり、継続監視や自動復旧の保証ではない。冗長化・自動再起動ポリシー・SLO・RTO／RPO・HTTPS終端は本構成では未整備。公開運用前に担当者・復旧目標・バックアップ／復元・監視とログ保管を決め、実環境で確認する。
