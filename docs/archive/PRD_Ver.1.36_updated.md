# 1. プロジェクト概要

## サービスコンセプト

> **忙しくても、子どもの学習に「意味のある関わり方」ができる。**

先生が採点済みの小学生のテストをAIで分析し、保護者に「苦手単元」と「次に取り組むべき学習」を提案するWebアプリ。

AIが採点するサービスではなく、保護者の学習サポートを目的とした分析サービスである。

> **「テストを撮るだけで、子どもの苦手が見える。」**

# 2. 課題設定（Issue）

## 誰の課題を解決するのか

### ペルソナ

- 共働きの30代夫婦
- 小学3年生の子どもがいる家庭
- フルタイム勤務で忙しい保護者
- 子どもの勉強を見たい気持ちはあるが時間がない。

## 現状の課題

1. テストは返却されても解き直しだけで終わる。
2. 苦手単元が蓄積されない。
3. 次に何を勉強すればよいか判断できない。
4. テスト分析に時間をかけられない。

## 理想の状態

AIがテストを分析し、

- 苦手単元を可視化する。
- 学習履歴を蓄積する。
- 優先して復習する内容を提示する。

保護者が迷わず子どもの学習をサポートできる状態を目指す。

# 3. 課題解決の考え方（本企画の軸）

## 本当の課題解決とは？

本当の意味で課題が解決した状態は、

> **子どもの学習行動が変わること**

と定義する。

しかし、MVPではそこまで実現することは難しいため、本企画では課題解決を2段階で考える。

## 第一段階（MVPで実現すること）

### 「忙しくても子どもに関わりたい」という親の気持ちを支援する

MVPでは **苦手単元の見える化** を提供価値とする。

### MVPで提供する価値

- 苦手単元を自動で整理する。
- 学習履歴として蓄積する。
- 「まずここから復習しよう」が分かる。
- テスト分析の時間を短縮する。

### 保護者に起こる変化

苦手が見える化されることで、

- 「忙しくても子どもに関われている。」
- 「何を勉強させればよいか分かる。」

という安心感につながる。

「今のままでいいのかな」という保護者のモヤモヤを和らげることを目指す。

### 家庭だけで終わらない価値

分析結果は、

- 学校の個人面談
- 担任の先生への相談
- 苦手単元の共有

など、学校とのコミュニケーションにも活用できる。

## 第二段階（将来的に目指すこと）

### 子どもの行動変容

将来的には、

- 間違え方に応じた学習方法の提案
- 類題・ドリル提案
- リマインド通知
- 学習目標の提示

など、子ども自身が行動を変えられるサポートまで広げる。

> **今回はMVP対象外（Phase2）とする。**

### MVPで提供する分析結果の見せ方（改訂：キャラクター・寄り添い型コメントを統合）

分析結果の核を「間違え方のパターン分析」に見直したことに伴い生まれた**キャラクターによる蓄積型コメント**と**長めのパーソナライズコメント（寄り添い型コメント）**は、当初Phase1候補（チーム内要検討）としていたが、企画レビューを経て**MVPに統合することを決定**した。

| 要素 | 内容 |
|---|---|
| マスコットキャラクター | 丸いアイコンで表現するキャラクターが、コメントの語り手として画面に表示される（MVP） |
| 長めのパーソナライズコメント（寄り添い型コメント） | 「労い→状況の説明→安心材料→次への後押し→締めの励まし」という型で、温かみのあるコメントを返す（MVP） |

**旧・一言ヒントとの統合**：これまで分析結果画面に短く表示していた「一言ヒント」は、独立した表示をやめ、**この長めのコメントの見出し（タイトル）として統合**する。分析結果画面では、一言ヒントに相当する短い文言をタイトルとして表示し、その下に寄り添い型の長めのコメント本文を続けて表示する構成とする。

**記録回数による出し分けは行わない**：当初検討していた「同一単元の記録が1回のみ／2回以上」による長さの出し分けは行わず、**常に長めのコメントを表示する**方針に変更した。これに伴い、「もっと詳しく見る」ボタンによる2段階表示も廃止し、分析結果画面に直接コメントを表示する。

### Phase2候補（分析機能の発展）

| 候補 | 内容 |
|---|---|
| 単元をまたいだ共通点の分析 | 間違え方のパターンを単元横断で集計し直し、「位置や大きさを正確に捉える力」のような、子ども固有の共通するつまずきを発見する |

この候補は、単元横断の集計という新しいロジックが必要な上、複数単元にまたがるまとまったデータ量が前提となるため、MVPの開発期間・データ量では十分に機能しにくい。Phase2として引き続き検討する。寄り添い型コメントは、将来的にこの分析結果も取り込む形に発展させることを見据える。

## MVPとPhase2の整理

## MVPの対象とするテスト 
MVPでは、先生による採点済みで、児童による解き直し・訂正が入る前のテストを主な解析対象とする。
児童による訂正が入った答案は、元の回答と訂正後の回答の判別が難しくなる可能性があるため、MVPでは主な解析対象とせず、Phase2以降の検討事項とする。

| MVP（今回実装） | Phase2（将来） |
|---|---|
| 採点済み・解き直し前答案の解析　| 解き直し・訂正済み答案への対応 |
| 間違え方のパターン分析 | 類題生成 |
| 寄り添い型コメント（キャラクター表示・タイトル＋長文） | リマインド通知 |
| 苦手単元ランキング（ホーム画面または設定画面に配置、詳細は未定） | 学習計画提案 |
| 学習履歴 | 子ども向け学習支援 |
| AI判定結果の保護者確認・修正ステップ | 単元をまたいだ共通点の分析 |

# 4. ソリューション（Solution）

## 分析結果として返す核の絞り込み（改訂）

当初、分析結果の核として「苦手単元ランキング」と「次への一言ヒント」の2点を採用していた。しかし、改めて検討した結果、**単元ごとの正答率を並べるだけでは、テストの束を見返せば親でも分かる情報であり、アプリならではの価値になっていない**という課題が見えてきた。

保護者が本当に効果を感じたいのは、「間違いの結果」の一覧ではなく、AIが**間違いの中身（間違え方）を分析してくれること**である。そこで、分析結果の核を以下のように改訂する。

| 候補 | 内容 | 採用可否 | 理由 |
|---|---|---|---|
| **間違え方のパターン分析** | 正誤の結果だけでなく、子どもが実際に書いた解答・計算過程から、間違え方の傾向（例：繰り上がりの計算ミス、位取りのミス、文章題の読み違いなど）を読み取る | 採用（核） | 単なる点数の並べ替えでは得られない、AIならではの分析価値。保護者が「相談材料」「安心感」を得るための本質的な情報 |
| **寄り添い型コメント（旧・次への一言ヒント）** | パターン分析の結果に応じた、キャラクターによる長めの声かけ。短い一言ヒントは、このコメントの見出し（タイトル）として統合する | 採用（核） | 定型的な「この単元を復習しましょう」ではなく、間違え方に即した具体性のあるヒントにする。企画レビューを経てPhase1候補からMVPへ格上げ |
| 苦手単元ランキング | 正答率が低い単元を順に並べる | 採用（表示場所は分析結果画面から変更） | 全体像を一覧で把握する用途で有用だが、分析結果画面の主役ではないため、ホーム画面または設定画面への配置に変更（詳細未定） |
| 正答率の推移（時系列グラフ） | 単元ごとの正答率が回を重ねるごとにどう変化しているか | 見送り（Phase2） | 変化が見える利点はあるが、グラフ表示は実装負荷が高く、MVPの記録量ではデータが少なく推移として機能しにくい |
| 記録頻度・継続状況のサマリー | どれくらい記録できているかの活動ログ | 見送り（Phase2） | 分析結果というより利用ログに近く、今回の核（間違え方のパターン分析）とは役割が異なる |
| 単元ごとのステータス表示（苦手／安定／得意） | 単元を状態別に分類して一覧化 | 見送り | 「得意」を扱う場合、判定基準の設計が新たに必要になり、MVPの範囲を超える |
| 直近と過去の比較コメント | 「前回よりこの単元が良くなっています」等 | 見送り（Phase2） | 有用だが、比較ロジックが複雑になり、実装期間（実質3週間）に見合わない |
| 優先順位つきのToDoリスト | ヒントを複数、優先順位付きで提示 | 見送り | 情報量が増え、「機能過剰にならないか」という講師の懸念に逆行するリスクがある |

**採用しなかった候補は、Phase2（第二段階：子どもの行動変容）で検討する候補としてストックしておく。**

### 🟢 決定済み：間違え方パターンの分類設計

「間違え方のパターン分析」は、**「単元固有のパターン」と「原因の種類」の2軸で整理する**方針とする。単元マスタとは別に、間違え方のパターンを分類・定義し、AIによる分析結果をこの考え方に沿って扱う。

さらに、分類は「単元固有のパターン」と「原因の種類」の2軸で捉える必要がある。

| 軸 | 内容 | 例 |
|---|---|---|
| 単元固有のパターン | どの種類の間違いか | 繰り上がりミス、分母の混同、文章題の読み違いなど |
| 原因の種類 | なぜ間違えたか | 空欄／ケアレスミス／理解不足 |

「原因の種類」については、判定の難易度・リスクが項目ごとに異なるため、以下の方針とする。

| 原因の種類 | 判定難易度 | MVPでの扱い | 声かけ例 |
|---|---|---|---|
| 空欄 | 低い（解答欄が未記入かどうかの検出のみ） | 確実に組み込む | 「今回、空欄のままだった問題がいくつかありました。時間が足りなかったのかもしれませんね。分からなくても、まずは書いてみることから始めてみましょう」 |
| ケアレスミス | 中（計算過程が書かれている場合のみ判定しやすい） | 計算過程が読み取れる場合に限り判定を試みる。難しい場合は無理に判定しない | （計算過程が読み取れた場合）「計算の考え方はできているようです。最後の答えを書き写すところで、数字が変わってしまったのかもしれません」／（読み取れない場合）「この問題は間違いになっていました。もう一度解いてみると、気づきがあるかもしれません」（原因は推測せず事実のみ伝える） |
| 理解不足 | 高い（誤判定のリスクが最も高い） | 断定的な表現を避け、「もしかすると理解が浅いかもしれません」等の柔らかい表現に留める、または判定自体をPhase2に回す | 「もしかすると、この考え方の部分は、まだ少し難しく感じているのかもしれません。一緒に確認してみるとよさそうです」（「理解できていません」等の断定表現は避ける） |

理解不足の誤判定は、親を必要以上に心配させるリスクがあるため、安全設計（子どもが見ても怖くならない言葉選び）の方針と合わせて慎重に扱う。判定の確からしさが低い項目ほど、声かけの表現も断定を避け柔らかくする、という対応関係を徹底する。

### 🟢 技術面への影響：検証済み

間違え方のパターンを分析するためには、先生がつけた○×だけでなく、**子どもが実際に書いた解答・計算過程・採点情報を画像から読み取る必要がある**。

実際の小学校算数テスト画像を用い、Vision対応LLMへ画像を直接入力して比較検証した。Stage A（画像から事実を抽出する工程）では、同じスマートフォン撮影画像3枚・同じ目的のプロンプトでGemma 4 26B A4B ITとGPT-5 Nanoを比較し、今回の検証条件ではGemmaの方が安定して内容を抽出した。

一方で、小数点の誤読（例：「4.5cm」を「45」と読む）などは残り、プロンプトを厳しくしても誤読を完全には防げなかった。このため、MVPでは**AIの読み取り結果を保護者が確認・修正してからパターン分析へ進む**設計とする。

なお、今回のPoCでは専用OCRとの比較検証は行っていないため、「OCRでは実現できない」とは断定しない。検証結果の詳細は別紙「AI画像読み取り・トリミング検証結果」を参照する。

## MVPで提供する機能（改訂）

| 機能 | 内容 |
|---|---|
| テスト画像アップロード・トリミング | 保護者がテストを撮影・アップロードする。必要に応じて、AI画像解析を行う前に氏名などの個人情報を含む部分を自由矩形でトリミングできる。トリミングは任意とし、問題番号・問題文・回答・採点情報はできるだけ残すよう画面上で案内する。 |
| AI画像解析（事実抽出） | 子どもの解答内容・正誤・問題番号・点数を、問題ごとに事実として抽出する（この段階では間違え方のパターン分析は行わない）。 |
| AI読み取り内容の確認・修正 | AIが**問題ごとに読み取った解答内容・正誤**を保護者が確認し、読み取りに誤りがあれば修正できるようにする（MVP必須要件、詳細は7章）。「この分析結果に同意するか」ではなく、「AIが解答を正しく読み取れているか（事実ベースの確認）」を確認する画面である。修正方法は自由入力（手入力）ではなく、**タップで選ぶ方式**とする（詳細は下記）。 |
| AI画像分析（パターン分析・単元推定） | **保護者による事実確認が完了した後**、確認済みのデータをもとに、間違え方のパターンを分析する。単元名が画像から取得できない場合は、問題内容から単元を推定し、判断できない場合は「判定困難」とする。 |
| 分析結果画面 | キャラクターによる寄り添い型コメント（タイトル＋長文）と、**過去の学習履歴（一覧）を1つの画面にまとめて表示**する。間違え方のパターン分析の結果を反映した内容とする。 |
| 苦手単元ランキング | ホーム画面または設定画面に配置する（詳細な配置場所は未定）。 |

> **MVPの処理フロー**  
> テスト撮影・アップロード  
> → 必要に応じて個人情報部分をトリミング  
> → AIによる画像読み取り（事実抽出）  
> → 保護者による確認・修正  
> → 間違え方のパターン分析  
> → 分析結果表示

### 🟢 確認と分析の順序について（重要な設計方針）

当初は、AIが間違え方のパターン（解釈）を先に提示し、それを保護者が確認・修正する設計だったが、**これは順序が逆であるという指摘を受け、見直した**。パターン（解釈）を確認・選択させる前に、まず**解答内容・正誤という事実そのものが正しく読み取れているかを確認**し、事実が確定してから初めて間違え方のパターンを分析する、という順序に変更する。

| Before（見直し前） | After（見直し後） |
|---|---|
| AIが間違え方のパターン（解釈）を提示 → 保護者がそのパターンの中から選び直す | AIが解答内容・正誤（事実）を提示 → 保護者が事実を確認・修正 → **確定した事実をもとに、間違え方のパターンをAIが分析** |

解釈（パターン）から確認させると、AIが決めつけた分類の中から選ばされる形になり、分析の意味が薄れてしまう。事実（何を書いたか、合っていたか）を先に確定させることで、その後のパターン分析がより正確かつ納得感のあるものになる。

### 分析結果画面と学習履歴の統合について

当初、分析結果画面と学習履歴画面は別々の画面として設計していたが、**学習履歴を分析結果画面に統合し、1画面にまとめる**方針に変更した。分析結果（最新のコメント）を見た流れのまま、これまでの記録も続けて確認できるようにするための変更である。

### 🟢 AI読み取り内容の修正方法：タップで選ぶ方式（決定）

修正方法は、自由入力（手入力）ではなく、**タップで選ぶ方式**とする。理由は以下の通り。

| 方式 | 親の手間 | 実装の複雑さ |
|---|---|---|
| 手入力（解答内容を自由に書き込む） | やや重い（何をどう書けばいいか迷う） | データの受け取り方・バリデーションなど、実装が複雑になりやすい |
| **タップで選ぶ（採用）** | 軽い（直感的、数秒で終わる） | シンプルな選択式のUIで済み、実装もしやすい |

**具体的な流れ（事実ベースの確認）**

「解答内容」と「正誤」は別々に間違っている可能性がある（例：解答内容の読み取りだけ間違っている、正誤の判定だけ間違っている、両方間違っている）ため、**1つの画面の中で、解答内容・正誤それぞれを独立して確認・修正できる**設計とする（別画面への遷移は行わない）。

1. AIが問題ごとに読み取った「解答内容」（例：子どもが書いた答え「6」）と「正誤」（○／✕）を、それぞれ表示する。
2. 「解答内容」に対して「○合っている／✕違う」のボタンを表示する。「✕違う」を選んだ場合のみ、その場に正しい解答内容を入力する欄が現れる。
3. 「正誤」に対しても同様に「○合っている／✕違う」のボタンを表示する。「✕違う」を選んだ場合のみ、その場に「○正解／✕不正解」を選び直すボタンが現れる。
4. どうしても当てはまらない場合のための、任意の一言メモ欄を補助的に用意する（必須ではない）。
5. 確認・修正が完了した後、その事実をもとにAIが間違え方のパターンを分析し、分析結果画面へ進む。

画面イメージ：ワイヤーフレーム⑤（別画面への遷移はなく、この1画面で完結する）。

忙しい親という前提を踏まえ、数秒でチェックが完了する操作性を優先し、実装もシンプルに保てる設計とする。

### 問題番号を抽出する理由

「AI画像解析」で問題番号も抽出する理由は、以下の3点である。

- **親が分析結果を確認できるようにするため**：AIが「繰り上がりでミスがあるようです」と分析結果を出す際、どの問題を指しているかが分かることで、親が元の問題に立ち返って確認・納得できるようにする。
- **AIの誤読み取りへの対策のため**：デメリット・リスク（7章）で挙げた「AIの誤分類」に対し、保護者が読み取り内容を確認・修正できる設計とするには、どの問題に対する判定かを特定できる必要がある。
- **開発・デバッグ時の検証のため**：AIの分析が正しく機能しているかをチームが確認する際、元の問題との対応関係を追跡できるようにする。

---

## AI分析イメージ（改訂）

1. テストを撮影する。
2. AIが画像を解析し、**問題ごとの解答内容・正誤・問題番号・点数を事実として抽出する**（この段階では間違え方のパターン分析は行わない）。
3. **保護者が、AIが読み取った解答内容・正誤を確認する**（解答内容・正誤それぞれに対して「○合っている／✕違う」をタップで選ぶ。MVP必須要件）。「✕違う」を選んだ場合は、その場（同一画面内）で解答内容または正誤を修正する（パターンの選択ではなく、事実の修正。別画面への遷移はなし）。
4. **確認・修正が完了した事実をもとに、AIが単元推定（必要な場合）と間違え方のパターン分類を行う**（事実確定後に初めて実行する）。単元名が読み取れている場合はその情報を利用し、単元名が欠落している場合は問題内容から「推定単元」を出す。判断できない場合は「判定困難」とする。
5. パターンに応じた寄り添い型コメント（タイトル＋長文）を生成する。タイトルは、その回の分析結果を表す一文とする（例：「繰り上がりでミスがあるようです」。過去の傾向を示す表現ではなく、今回の結果を表す表現にする）。長文本文は、具体的な確認方法まで踏み込んだ内容とする（例：「今回のテストでは、わり算の『あまり』の部分で間違いが見られました。あまりの計算は多くのお子さんがつまずきやすいところです。問3を見ると、あまりが割る数より大きくなってしまっているようなので、『あまりは割る数より小さくなるはず』ということを一緒に確認してみると、コツをつかみやすいかもしれません。焦らず、少しずつで大丈夫ですよ。」）。「ここ数回のテストを見てみると」のような、過去の蓄積を前提とした表現は用いず、今回1回の結果として書く。
6. 苦手単元ランキングを算出する（ホーム画面または設定画面に表示）。
7. 分析結果画面に、寄り添い型コメントと学習履歴をあわせて表示・保存する。

> **注釈**：旧「一言ヒント」（短い一文）は独立した表示をやめ、寄り添い型コメントの見出し（タイトル）として統合した。同一単元の記録回数による長さの出し分け（1回のみ／2回以上）は行わず、常に長めのコメントを表示する。キャラクター（丸いアイコン）の表示、寄り添い型コメントは、企画レビューを経てPhase1候補からMVPへ統合した（詳細は3章を参照）。

## 寄り添い型コメントのトーン・スタイル例

チームとしては当初から、間違え方のパターンごとにヒント文を固定的に用意する（分類方式）のではなく、**汎用プロンプトを用いてAIにその都度ヒントを生成させる方式（生成方式）を想定**していた。そのため、以下の表は「選択する固定パターン集」ではなく、**AIに生成させたい文体・トーンを具体化するための参考例（スタイルガイド）**という位置づけである。表の内容は、寄り添い型コメントの**タイトル部分**の生成に使う想定（本文は「労い→状況の説明→安心材料→次への後押し→締めの励まし」の型で別途生成する）。

| 間違え方のパターン（例） | トーン例①（気づきを促す） | トーン例②（具体的な後押し） | トーン例③（前向きな声かけ重視） |
|---|---|---|---|
| わり算：九九の定着不足 | 九九をもう一度、声に出して確認してみましょう | わり算でつまずく時は、まず九九の復習から始めるのがおすすめです | 九九はあと少しの練習で、ぐっと得意になりますよ |
| わり算：あまりの扱いミス | 「あまり」の意味をもう一度確認してみましょう | あまりが割る数より大きくないか、見直す習慣をつけてみましょう | あまりの計算は伸びしろが大きいところです |
| 分数：分母の混同 | 分母が同じかどうか、まず確認する癖をつけてみましょう | 同じ分母どうしの計算から、もう一度練習してみましょう | 分数は「慣れ」で伸びる単元。焦らず一緒に取り組みましょう |
| 分数：通分・約分ミス | 通分のやり方を教科書で振り返ってみましょう | 小さい数から順番に、約分の練習をしてみましょう | 分数の考え方が身についてきている証拠でもあります |
| 円：半径と直径の混同 | 半径と直径、どちらを聞かれているか確認してみましょう | 円の絵を描いて、半径と直径の違いを目で確認してみましょう | 図形は「見て覚える」のが得意な子も多い単元です |
| 文章題：読み違い | 何を聞かれているか、線を引きながら読んでみましょう | 文章題は、まず数字と言葉を整理することから始めてみましょう | 文章題は大人でも難しいもの。ゆっくりで大丈夫です |
| 文章題：立式ミス（何算か迷う） | たし算・ひき算・かけ算・わり算、どれを使うか一緒に考えてみましょう | 似た問題を1つ、一緒に解いてみるのがおすすめです | 式を立てる力は、これからぐんと伸びていきます |
| 繰り上がり・繰り下がりのミス | 10のまとまりを意識しながら計算してみましょう | 繰り上がりのある計算だけ、少し練習してみましょう | 計算のスピードも、あと少しで安定してきますよ |

### トーンの設計意図（プロンプトに反映する方針）

- **①気づきを促す系**：「〜してみましょう」で、親子で一緒に確認する行動を促す。
- **②具体的な後押し系**：何を、どう練習すればいいかまで踏み込む。
- **③前向きな声かけ重視系**：「伸びしろ」「あと少し」のトーンを強調し、感情面のケアを優先する。

いずれのトーンも、断定表現を避け、責めない・前向きな言葉選びをする、という安全設計の方針（後述）と一貫させる。

# 5. MVPの範囲

## 対象範囲（決定）

### 🟢 決定済み

**対象とするテストの種類**

- 単元テストのみを対象とする（1回のテスト＝1つの単元という前提）
- まとめテスト（複数単元が混在するテスト）は対象外とする

**対象教科**

- 算数のみ

**対象学年**

- 小学3年生のみ
- 4・5・6年生向けの機能は、将来的に実現したいものとしてPhase2候補に位置づける

### 理由

- 実装期間が実質3週間であるため。
- AIプロンプトをシンプルに設計できる。
- 単元数を限定できる。
- 単元テストに絞ることで、テストの点数がそのまま単元の正答率として扱え、AIの読み取り・データ設計がシンプルになる（詳細は「テストの種類について」資料を参照）。

---

## MVP対象単元（例）

| 学年 | 対象単元 |
|---|---|
| 小3 | わり算・たし算とひき算の筆算（初期検証の推奨2単元） |

### 🟢 方針確定：対象単元の絞り込みと、汎用プロンプトによる拡張可能性

小3算数の単元は、教科書会社によって多少の差はあるが実際には18単元前後（かけ算、時こくと時間、わり算、たし算とひき算の筆算、長さ、ぼうグラフと表、暗算、あまりのあるわり算、大きい数のしくみ、かけ算の筆算、円と球、重さ、三角形、小数、分数、計算のきまり、□を使った式、表とグラフの整理　等）存在する。

間違え方のパターンは、あらかじめ選択肢として固定的に用意する方式（分類方式）だけでなく、AIに「この解答のどこで、どう間違えたかを説明してください」という汎用的な指示を与え、その都度パターンを生成させる方式（生成方式）でも実現できる。生成方式であれば、理論上は単元ごとにパターンを手作業で用意する必要がなく、より多くの単元に対応できる可能性がある。

ただし、対象単元を絞る理由は「パターンを人手で書ききれないから」だけではなく、以下の理由が別途ある。

| 理由 | 内容 |
|---|---|
| 単元マスタの整備 | 単元が増えるほど、教科書会社間の単元名の表記ゆれ対応（名寄せ）の準備が増える |
| 単元の性質による精度のばらつき | 計算系（わり算・筆算等）、図形系（三角形・円と球等）、文章題（読解系）では、間違え方の説明のしやすさ・AIの得意不得意が異なる可能性があり、単元の性質ごとに検証が必要 |
| テスト設計のしやすさ | AIの出力が完全に自由だと、何をもって「正しい」とするかのテストが書きにくくなる。範囲がある程度絞られている方が品質検証がしやすい |

そのため、MVPでは小3算数・単元テストに対象を絞る方針を維持する。一方、今回のStage A検証では、小数・分数・筆算・図形を含む複数の答案画像に対して、同じ目的のプロンプトで内容抽出を行えることを確認した。これにより、画像読み取り工程では単元ごとに完全に別の読み取り方式を用意しなくても対応できる可能性が確認できた。

ただし、**Stage B（間違え方のパターン分析）における汎用プロンプトの精度は別途検証が必要**であり、全単元への対応を保証するものではない。

### 初期検証としておすすめする単元

絞り込みの基準（つまずきやすいか／他の単元の土台になるか）に加え、まずは性質の近い単元同士で汎用プロンプトを検証し、その後に性質の異なる単元（図形・文章題）へ広げる、という段階的な進め方を推奨する。

| 段階 | 単元 | 選定理由 |
|---|---|---|
| 第1段階（最初に検証） | わり算（あまりのあるわり算を含む） | つまずきやすく（あまりの処理ミス等）、上位学年の割り算・分数の土台になる。計算系のため間違え方が構造的に捉えやすく、プロンプト検証に向く |
| 第1段階（最初に検証） | たし算とひき算の筆算 | 繰り上がり・繰り下がりミスなど、間違え方の型が明確で検証しやすい。すべての計算の基礎となる土台的な単元 |
| 第2段階（うまく機能すれば拡張） | かけ算の筆算、分数 | いずれも上位学年の学習の土台になる。計算系のため、第1段階で検証した汎用プロンプトの延長で対応しやすいと考えられる |
| 第3段階（別途検証が必要） | 円と球、三角形（図形系）、文章題（読解系） | 計算系とは間違え方の性質が異なるため、同じプロンプトで同水準の精度が出るか別途検証が必要 |

MVPの対象は小3算数・単元テストとし、実装・検証ではまず少数の単元から確認する。対応単元の拡張は、Stage Bの分析精度を確認しながら段階的に行う。

# 8. 著作権・データ保存方針

## 前提

講師コメントを踏まえた設計方針。

- デモでは著作権フリーまたは利用許諾済み教材を使用する。
- 学習課題として設計する。
- 商用利用は想定しない。

---

## データ保存方針（提案）

| 保存する情報 | 保存しない情報 |
|---|---|
| 教科 | テスト画像 |
| 点数 | 問題画像 |
| 苦手単元 | 採点済み答案画像 |
| 間違えた問題番号 | OCR全文テキスト |
| AIコメント | — |

### 点数を保存する理由

苦手単元ランキングには直接使わない情報だが、以下の2つの用途のために保存する。

- **個人面談で使える材料にするため**：学校の個人面談で先生に相談する際、点数の推移も合わせて見せられると、会話の具体的なきっかけになる。
- **苦手が克服できたかどうかの指標にするため**：単元ごとの正誤だけでなく、点数の推移を見ることで、苦手が実際に改善しているかを確認する一つの目安にする。

### この設計の目的

- 著作権への配慮。
- 必要最小限のデータ保存。
- 学習履歴だけを蓄積する。

### 🟢 決定済み

- 画像は解析後に削除する。分析結果（教科・点数・苦手単元・間違えた問題番号・AIコメント等）のみをデータベースに保存する。
- ただし、保護者によるAI判定結果の確認・修正ステップ（MVP必須要件、セクション7参照）は、画像削除の前に行う想定とする。確認ステップを終え、保護者が結果を確定した後に画像を削除し、分析結果のみを保存する、という順序になる。

## 個人情報のマスキング方針

### 🟢 決定済み：A案（保護者による任意トリミング）

学校のテストには氏名・組・番号などの個人情報が記載されているため、外部AIへ送信する前に、それらが写り込まないようにする配慮が必要となる。PoC検証の結果、以下の4案を比較し、A案を採用することを決定した。

| 案 | 方法 | 採否 |
|---|---|---|
| **A（採用）** | 保護者が手動でトリミング・黒塗り（任意） | 🟢採用 |
| B | アプリで自動マスク | 見送り |
| C | 自動マスク＋保護者確認 | 見送り |
| D | 自動マスク＋確認・修正UI | 見送り |

**採用理由**

- B〜D案（自動マスキング）は、実装工数がA案（約4〜12時間）に対し24時間以上と大きく、実装期間（実質3週間）を踏まえると負担が大きい。
- C案は当初有力候補だったが、撮影のたびに確認画面を挟むと、忙しい保護者にとって操作のもたつきを感じさせる可能性があり、MVPの必須機能ではなく「あったらいいな」の位置づけであることも踏まえ、より軽量なA案に変更した。
- A案は、撮影後にトリミング画面へ遷移し、トリミングしたい保護者は行い、不要な保護者はそのまま進める、という設計とする。操作は完全に保護者の任意とし、「氏名などが写り込んでいないか確認してください」という一言を添えて軽く後押しする。

**前提となる安全設計**

トリミングを行わなかった場合でも、以下の設計によって個人情報のリスクを抑える。

- アプリ側でテスト画像を保存しない（セクション8「データ保存方針」参照）
- 外部AIとの接続はZDR（Zero Data Retention）対応Endpointのみを利用し、AI提供側でもデータを保持しない設計とする（詳細はセクション9参照）

# 9. AI画像解析方式（技術比較）

## 🔵 技術検証して決める

| 方式 | メリット | デメリット |
|---|---|---|
| Vision対応LLM | 実装がシンプル・画像理解が得意。 | API料金・プロンプト設計。 |
| OCR → LLM | テキスト構造化しやすい。 | OCR実装が追加になる。 |
| OCRのみ | 無料・高速。 | 単元分類が難しい。 |

## 🟢 AI接続方法：決定済み（OpenRouter経由）

スマートフォン → アプリ → OpenRouter → Provider／Endpoint → Vision LLM → 解析結果、という構成で接続する。

**決定理由**

- OpenRouterには、ZDR（Zero Data Retention）ポリシーを持つEndpointにのみルーティングする設定があり、個人情報を保持しない設計を実現できる（出典：OpenRouter公式ドキュメント [Zero Data Retention](https://openrouter.ai/docs/features/zdr)）。
- スクール配布のAPIキーがOpenRouter用であり、実装上もこの方法一択となる。
- 「アプリで画像を保存しない」ことと「外部AI側でも保持されない」ことは別の観点であり、両方を満たす設計とする。ZDR対応Endpointは、Provider名だけでなく実際に使用するEndpoint単位でも確認する（技術選定時に事前確認→実装時に再確認）。

### 🟢 使用モデル：Gemma 4 26B A4B（Stage A / Stage B）

スクールから配布されたAPIキー（OpenRouter経由）で利用できるのは以下の8モデルに限定される。

| モデル | 提供元 | 用途 |
|---|---|---|
| DeepSeek V4 Flash 0731 | DeepSeek | チャット・テキスト生成 |
| GLM 4.7 Flash | Z.ai（Zhipu） | チャット・テキスト生成 |

このうち、**画像入力（Vision）に対応しているGPT-5 NanoとGemma 4 26B A4Bを実画像で比較検証した**。今回のStage A検証ではGemmaの方が安定して内容を抽出したため、Stage AではGemma 4 26B A4Bを採用する。

Stage BについてもGemma 4 26B A4Bで簡易検証を実施した。確認済みデータを入力し、①小数点の位置の誤り、②空欄、③途中式から確認できる計算手順の誤り、の3ケースで、定義した「単元固有のパターン」と「原因の種類」の分類方針に沿った出力を確認した。特に、根拠が不足する原因について「理解不足」「ケアレスミス」と断定せず「判定困難」とする挙動を確認した。

以上から、**MVPではStage A / Stage BともにGemma 4 26B A4Bを使用する**。モデルを統一することで、API接続・設定・エラー処理などの実装をシンプルにする。なお、今回のStage B検証は3ケースによる簡易検証であり、すべての問題・単元での精度を保証するものではない。今後も実装・テストの中で継続検証する。

**GPT-5 Nano と Gemma 4 26B A4B の比較（参考情報）**

| 項目 | GPT-5 Nano | Gemma 4 26B A4B |
|---|---|---|
| 位置づけ | GPT-5ファミリーの最軽量モデル | MoE（Mixture of Experts）アーキテクチャ、26Bパラメータ中4Bを活性化 |
| 視覚系ベンチマーク（参考） | 視覚理解62.7%、OCR62.5%（前世代GPT-5.4 Nanoの第三者検証値） | MMMU Pro 73.8%、MATH-Vision 82.4%（公式発表のベンチマーク値） |
| 備考 | 軽量・低コスト志向のモデル | 同程度のパラメータ規模の中では高精度とされる |

数値上はGemma 4 26B A4Bの方がベンチマークスコアが高い傾向にあるが、測定条件（ベンチマークの種類、非公式検証か公式発表か）が異なるため単純比較はできない。日本語の手書き文字読み取りという、本サービス特有のタスクでの精度は、どちらのモデルも実際に検証してみないと分からない。

なお、GPT Image 1 Mini（画像生成）は分析には使えないが、Phase1候補のキャラクターのビジュアル素材を生成する用途に転用できる可能性がある。

### 🟢 精度検証：実施済み（継続検証あり）

実際の小3算数の答案画像を用いて、GPT-5 NanoとGemma 4 26B A4Bの画像読み取りを比較した。今回の条件では、Gemmaは3/3枚で内容を抽出し、GPT-5 Nanoは1/3枚で内容を抽出したため、Stage AではGemmaの方が安定していた。

ただし、Gemmaでも小数点の誤読や、画像を切りすぎた場合の問題番号の誤認・問題欠落が確認された。また、モデルが「自信なし」と表示しない誤読もあるため、**LLMの出力を自動確定しないこと**をMVPの設計方針とする。

この検証結果を受け、Stage AではGemmaを採用し、保護者による確認・修正ステップを必須とする。

Stage Bでは、分類能力を確認するため、**実際の答案の誤りを再現したものではなく、異なる誤答パターンを想定して作成した検証用データ**を3ケース入力した。Stage Bには画像を直接渡さず、Stage A後に保護者が確認・修正した「確認済みデータ」を想定したテキスト情報のみを入力した。

| ケース | 想定した誤答パターン | 出力結果 | 評価 |
|---|---|---|---|
| Case 1 | 小数：正答4.5cmに対して45cmと回答したと想定 | 小数点の位置の誤り／原因は判定困難 | ○ |
| Case 2 | わり算：回答が空欄だったと想定 | 単元固有パターンは判定困難／原因は空欄 | ○ |
| Case 3 | たし算の筆算：繰り上がりを次の位に加えなかったと想定 | 計算手順の誤り／原因は判定困難 | ○ |

今回の3ケースでは、3/3ケースで事前に想定した分類方針に沿った出力を確認した。特に、誤りの内容は具体的に分類しながら、根拠が不足する場合には「ケアレスミス」「理解不足」と断定せず「判定困難」とする挙動を確認できた。ただし、**3/3は今回の検証ケースで期待した挙動が得られた件数であり、Stage B全体の分析精度100%を意味しない**。ケース数が少ないため、MVP採用可否を判断する初期検証として扱い、実装後も継続検証する。

### 単元名が欠落した場合の推定検証

トリミングで単元名が画像から除外される場合を想定し、単元名を入力せず、問題内容・解答・正答・途中式などの確認済みデータだけからGemma 4 26B A4Bが単元を推定できるかを3ケースで確認した。

| ケース | 入力した問題の種類 | Gemmaの推定 | 評価 |
|---|---|---|---|
| Case 1 | 4cm5mmをcmで表す問題 | 長さ（小数の表し方）／確実性：高 | ○ |
| Case 2 | 24個を6人に同じ数ずつ分ける問題 | わり算／確実性：高 | ○ |
| Case 3 | 368+457の筆算 | 三桁の数のたし算／確実性：高 | ○ |

今回の3ケースでは、3/3ケースで想定した単元に沿った推定結果が得られた。ただし、これも3ケースのみの簡易検証であり、全単元・全問題形式での単元推定精度を示すものではない。MVPでは、単元名が取得できた場合はその情報を利用し、取得できない場合のみStage Bで問題内容から「推定単元」を出す。判断できない場合は「判定困難」とする。

### PoCではどのようにAIへ接続して検証したか

検証は、WSL（Ubuntu）上で作成したPythonスクリプトからAI APIへリクエストを送る形で実施した。画像読み取り検証ではテスト画像とプロンプトを、Stage B・単元推定検証では確認済みデータを想定したテキストとプロンプトを送信し、返却されたモデル出力を保存・比較した。

今回のGemmaのStage B・単元推定の簡易検証では、**Google Generative Language APIへ検証用APIキーで直接接続**して `gemma-4-26b-a4b-it` を呼び出した。これはモデルの挙動を短時間で確認するPoC用の接続方法である。

一方、**MVP実装ではOpenRouter経由でGemmaを利用する予定**であり、ZDR対応Endpointを選択する。したがって、PoCで確認したモデルの挙動をそのまま本番経路の保証とはせず、実装時にはOpenRouter経由でも同じ代表ケースを再テストする。

> PoC：ローカルPython → AI API → Gemma → 結果を保存・比較  
> MVP：ブラウザ → Next.js / FastAPI → OpenRouter（ZDR）→ Gemma → Stage A / 確認修正 / Stage B

- **未定の点**：しきい値となる回数、超過後の料金、無料枠を使い切った場合の挙動（利用をブロックするか、追加課金で継続できるようにするか）

**キャラクターの着せ替え案（検討中のたたき台）**

チームで最も具体的に話が進んだ案の一つ。以下はその設計のたたき台であり、採用が決まったものではない。

- **基本方針**：無料の範囲（分析結果、寄り添い型コメント、キャラクターの標準の見た目）はMVPのコア機能としてすべて提供する。有料の範囲は、キャラクターの見た目を変える「着せ替え（コスチューム）」の追加購入とする。
- **Pay-to-lookの原則（Pay-to-winにしない）**：課金しても分析の精度やヒントの質は変わらない設計とする。「課金しないと十分な分析が受けられない」という設計は、忙しい親の不安につけこむ形になりかねないため避ける。
- **購入導線のイメージ**：分析結果画面のキャラクターをタップ→きせかえショップ画面へ→コスチュームを選択→購入（Stripe決済、または構想のみのモック）。
- **安全面の配慮**：子どもが単独で購入操作をしてしまわないよう、保護者のアカウントでのみ購入操作ができる設計とする。

# 11. 価格試算（参考）

## 🟡 チームで議論する（あくまで参考値）

本セクションは、実際に利用者へ課金することを想定したものではなく、**もしこのサービスをビジネスとして展開した場合、利用者にいくら課金すべきかを試算した、仮定の参考値**である。今回はスクールの卒業制作としてMVPを実装することが目的であり、決済機能（Stripe）自体は課題のMUST要件として実装するが、実際の運用では架空の利用者・架空の金額でのデモにとどまる想定である。

### 算出方法

```
月額利用料の目安 = (固定費 ÷ 想定ユーザー数) + (1回あたりの解析費用 × 月間利用回数) + 余裕分
```

### 固定費（サーバー代）

EC2 t3.smallの構成で、1日あたり約800〜1,000円という情報から、

> 900円/日（中間値）× 30日 = **月額約27,000円**

をベースの固定費とする。RDS・Memcached等を含めた総額かどうかは要確認。

### 従量費（AI解析1回あたり）

Vision対応LLM（GPT-4o）の料金（入力$2.50／100万トークン、出力$10／100万トークン）をもとに試算すると、テスト画像1枚の解析で **約1円/回**。画像解像度やプロンプト量による変動を見込み、余裕を持って **2〜5円/回** を想定する。（OCRのみの方式であれば、さらに安価になる可能性がある）

### 想定ユーザー数別シミュレーション（1人あたり月8回記録と仮定）

| 想定ユーザー数 | 固定費 | 従量費（2円×8回×人数） | 合計 | 1人あたり月額 |
|---|---|---|---|---|
| 50人 | 27,000円 | 800円 | 27,800円 | 約556円 |
| 100人 | 27,000円 | 1,600円 | 28,600円 | 約286円 |
| 500人 | 27,000円 | 8,000円 | 35,000円 | 約70円 |

### 分かること

- ユーザー数が増えるほど、1人あたりのコストは急激に下がる（固定費を多くの人数で分け合えるため）。100人規模であれば、他社事例（300〜500円/月）とほぼ近い水準に収まる。
- 少人数（卒業制作のデモ規模など）では、価格だけ見るとコストが上回る可能性があるが、卒業制作段階では収益化よりMVPの実現を優先する。

### 注意点

- トークン数の見積もりは概算であり、実際のAPI検証（画像サイズ・プロンプト設計）によって変動する。
- Stripeの決済手数料、Memcachedの追加費用、安価なリージョン選定は、この試算にまだ含まれていない。
- 「ざっくりAWS」（[https://aws-rough.cc/](https://aws-rough.cc/)）で、実際のチーム構成に近い形での再試算を推奨する。
