# Backend コーディング規約

> 対象：学習トラッキングアプリ（仮） / Team-A\
> Backend：FastAPI + Python\
> 基準：PRD Ver.1.37 / Backend環境構築Issue\
> 目的：Backend担当2人が並行開発するときの品質統一・責務分離・Gitコンフリクト低減

---

## 1. この規約の目的

本規約は、コードを「きれいに書く」ことだけを目的としません。

Backend担当2人が短期間で並行開発するため、次を共通ルールとします。

- 誰が書いても同じ考え方で読める
- 機能ごとの担当範囲を分ける
- 同じファイルを2人が同時に編集する状況を減らす
- `main.py` などの共通ファイルを肥大化させない
- API・DB・AI・外部サービスの責務を混ぜない
- AIの誤読・過剰推測をコード設計でも防ぎやすくする
- APIキーや個人情報を安全に扱う

迷った場合は、**「その処理はどの機能の責務か」**を基準に配置を判断します。

---

## 2. 基本方針

### Python

Pythonの一般的なスタイルとして **PEP 8** を基本とします。

ただし、Ruffによる自動整形結果を優先します（詳細は「Formatter / Linter」を参照）。

### シンプルさを優先する

MVPでは過度な抽象化を避けます。

- 将来使うかもしれない、だけで共通化しない
- 1回しか使わない処理を無理にutility化しない
- 複数機能で実際に必要になった時点で共通化する
- 初学者でも追える構造を優先する

## 3. Backendの基本構成

Backendは、**Backend担当2人による並行開発を前提としたFeature-based（機能単位）の構成**とします。

> ディレクトリ構成の一覧は、**Backend環境構築Issueの構成図を正**とします。
> 構成図をこの規約に重ねて持つと、更新時にずれるため、ここには載せません。

### ディレクトリ構成の方針

原則として、**機能固有のコードは `app/features/<feature>/` 内で完結**させます。

各機能の中では、必要に応じて責務ごとにファイルを分割します。

- `router.py`：APIの入口
- `service.py`：ビジネスロジック・処理順序の制御
- `repository.py`：DBアクセス
- `schemas.py`：Request / Response等のデータ構造
- `client.py` / `clients/`：外部サービスとの通信

> DBモデル（テーブル定義）は、featureの中には置きません。すべて `app/db/models/` に置きます（後述）。

AI機能は、Stage A / Stage BのプロンプトとOpenRouter接続も分離します。

この構成の目的は、ファイルを細かく分けること自体ではありません。
**2人が同じファイルを同時に編集する機会を減らし、Gitコンフリクトを抑えながら並行開発しやすくすること**を目的とします。

ただし、MVPでは必要以上にファイルを細分化しません。
機能の規模と責務に応じて必要なファイルのみ作成し、初学者でも処理を追いやすい構成を優先します。

### feature間の依存の向き

featureどうしが循環して参照し合わないよう、呼び出しの向きを一方向に固定します。

```text
test_analysis → ai_analysis
test_analysis → usage
test_analysis → learning_history
usage         → payment（有料プランかどうかの判定）
```

- `test_analysis` は、フロントから見た分析フローの入口です。入力検証と、他featureを呼ぶ順序の制御を担当します。
- `ai_analysis` はAI処理を担当し、フロントに公開するrouterは持ちません。他featureを呼びません。
- 逆向きのimport（例：`ai_analysis` から `learning_history` を呼ぶ）はしません。
- 他featureは、その `service.py` を経由して呼び出します。他featureの `repository.py` を直接呼びません。
- 向きを変える必要が出た場合は、もう一人のBackend担当に相談し、Issueとこの規約を更新します。

## 4. ファイルごとの責務

### `router.py`

HTTPリクエストの入口です。

担当するもの：

- URL
- HTTP Method
- Requestの受け取り
- Responseの返却
- Dependency
- 適切なserviceの呼び出し

複雑なビジネスロジック、AI処理、DB Queryを直接書きません。

```python
@router.post("/analyses")  # URLは例。最終的なURLはAPI仕様書を正とする
def create_analysis(
    request: ConfirmedAnalysisRequest,
    current_user: Annotated[User, Depends(get_current_user)],
) -> AnalysisResponse:
    return test_analysis_service.run_stage_b(current_user.id, request)
```

> `user_id` はリクエストのbodyやクエリから受け取らず、認証Dependencyから取得します（「セキュリティ」を参照）。
>
> `Depends()` は、デフォルト引数ではなく `Annotated[..., Depends(...)]` の形で書きます。

### `service.py`

機能の中心となる処理を担当します。

例：

- データの組み立て
- 処理順序の制御
- repositoryの呼び出し
- 外部clientの呼び出し
- 他featureの `service.py` の呼び出し（依存の向きに従う）

### `repository.py`

DBアクセスを担当します。

例：

- SELECT
- INSERT
- UPDATE
- DELETE

DB Queryをrouterへ直接書きません。

### `schemas.py`

APIのRequest / Response等、データ構造を定義します。

### `client.py` / `clients/`

外部サービスへの通信を担当します。

例：

```text
OpenRouter
Stripe
```

外部APIへのHTTPリクエストをrouterや複数のserviceへ散らしません。

## 5. 命名規則

### ファイル・ディレクトリ

`snake_case` を使用します。

```text
ai_analysis/
learning_history/
test_analysis/
openrouter.py
```

### 変数・関数

`snake_case`

```python
test_result = ...
user_id = ...

def create_analysis():
    ...
```

### クラス

`PascalCase`

```python
class AnalysisRequest:
    ...

class OpenRouterClient:
    ...
```

### 定数

`UPPER_SNAKE_CASE`

```python
MAX_RETRY_COUNT = 3
DEFAULT_TIMEOUT_SECONDS = 30
```

> モデル名やタイムアウトなど、環境ごとに変えたい設定値は定数に直書きせず、環境変数から読みます（「AIモデル名・設定値」を参照）。

### Boolean

意味が分かる名前にします。

```python
is_authenticated
has_analysis_result
is_confirmed
```

曖昧な名前は避けます。

```python
flag
check
data2
temp
```

## 6. 型ヒント

関数の引数と戻り値には、原則として型ヒントを付けます。

```python
def get_user(user_id: str) -> User:
    ...
```

戻り値がない場合：

```python
def log_event(message: str) -> None:
    ...
```

`Any` の多用は避けます。

---

## 7. 関数

1つの関数には、できるだけ1つの責務を持たせます。

避けたい例：

```python
def analyze_and_save_and_send_payment_and_log():
    ...
```

処理を分けます。

```python
def analyze_test():
    ...

def save_analysis():
    ...

def record_usage():
    ...
```

ただし、細かく分割しすぎて処理を追いにくくしないよう注意します。

## 8. 同期 / 非同期の方針

Stripe SDK、pymemcache、firebase-admin、SQLModelのSessionは**同期処理**です。
`async def` の中でこれらを呼ぶと、処理が終わるまでサーバー全体が止まります。

初期方針として、次のように統一します（チーム合意後に確定）。

- router・service・repository・clientは、原則としてすべて `def`（同期）で書く。
- OpenRouterへのHTTP通信も、同期のHTTPクライアントで行う。FastAPIは `def` のエンドポイントを別スレッドで実行するため、AI呼び出しに時間がかかっても、他のリクエストは処理される。
- `async def` を使う場合は、その理由をPRに書き、同期処理を中で呼んでいないことを確認する。
- `async def` と `def` を、同じ呼び出しの流れの中で混在させない。

## 9. `main.py` のルール

`main.py` はFastAPIアプリの入口として薄く保ちます。

書いてよいもの：

- FastAPIアプリ生成
- middleware設定（CORSなど）
- 共通routerの登録（`api/router.py` にまとめたrouterを読み込む）
- startup / shutdownなどのアプリ全体設定

書かないもの：

- Stage A / Stage Bのプロンプト
- SQL Query
- Firebase認証の詳細処理
- Stripe決済処理
- 学習履歴処理
- 画像解析ロジック

## 10. APIルーター

機能ごとにrouterを分けます。

```text
features/
├── auth/router.py
├── test_analysis/router.py      ← 分析フローの入口（Stage A用・Stage B用）
├── learning_history/router.py
├── usage/router.py
└── payment/router.py
```

`ai_analysis` はfeature内部の処理のため、routerを持ちません。

1つの巨大な `routes.py` に全APIを書きません。

### API URL

RESTを意識し、原則として名詞を使用します。

例：

```text
/analyses
/history
/usage
```

最終的なエンドポイント名はAPI仕様書を正とします。

## 11. Request / Response

APIから返すデータ構造を明確にします。

可能な限りschemaを通して返します。

避けたい例：

```python
return {
    "a": value1,
    "b": value2,
}
```

推奨（例）：

```python
return AnalysisResponse(
    unit=unit,
    mistake_patterns=mistake_patterns,
    comment_title=comment_title,
    comment_body=comment_body,
)
```

- AIの生レスポンスをそのままFrontendへ返す設計は避けます。
- **DBモデル（`table=True`）をそのままResponseとして返しません。** 返すデータは `schemas.py` の型に変換します（DB側の項目が意図せず公開されるのを防ぐため）。
- エラーレスポンスに、内部の例外メッセージ、スタックトレース、AIの生出力、個人情報を含めません。

---

## 12. DBアクセス

PostgreSQL + SQLModelを使用します。

DB接続などの共通設定：

```text
app/db/
```

機能固有のDB処理：

```text
features/<feature>/repository.py
```

routerから直接DB Queryを実行しません。

### テーブル定義の置き場所

- **すべてのDBモデル（テーブル定義）は、どのfeatureから使うかに関わらず `app/db/models/` に置きます。** ユーザー・単元マスタ・分析記録だけでなく、利用回数・決済状態のテーブルも、ここに含めます（みなみさんの提案を採用：「featureから見た利用先」ではなく「DBモデルであるか」で置き場所を統一する）。
- **1テーブル＝1ファイル**とします（例：`db/models/usage.py`、`db/models/payment.py`）。テーブルの把握・リレーション確認・追加ルールをシンプルに保つためです。
- featureのフォルダには、そのモデルを使う `service.py`・`repository.py`・`schemas.py` などの機能固有の処理だけを置きます。`repository.py`は、テーブル定義（設計図）を使って、実際にDBへ読み書きする処理なので、引き続きfeatureに残ります。
- すべてのモデルが読み込まれるよう、読み込む場所を1か所（例：`db/models/__init__.py`）に決めます。テーブルを追加するときに編集する共有ファイルなので、変更時はもう一人のBackend担当に共有します。

### SQLの書き方

SQLを文字列連結（f-stringなど）で組み立てません。SQLModel / SQLAlchemyのクエリ、またはパラメータ指定を使います（SQLインジェクション対策）。

### Transaction

複数のDB更新を一連の処理として扱う必要がある場合は、途中失敗時の整合性を考慮します。

特に、**分析結果の保存と利用回数の加算**は、片方だけ成功するとずれます（利用回数は課金判定に使う重要な記録です）。この2つを同一transactionで扱うかは、利用回数の方式を決める際に一緒に決めます。

具体的なtransaction管理方法は、DB実装確定後に統一します。

## 13. AI関連の重要ルール

AI関連は本プロジェクト特有の重要な規約です。

### Stage AとStage Bを混ぜない

```text
Stage A
画像 → 見えている事実の抽出

保護者による確認・修正（フロント側で実施）

Stage B
確認済みデータ → 単元推定・間違え方分析
```

- Stage Aのコードで学習理解度や原因分析を行いません。
- Stage Bへ未確認のStage A結果を直接渡す処理を基本フローにしません。
- Stage Bには**画像を渡しません**。確認済みのテキストデータのみを渡します。
- Backendは、確認・修正の間の状態を保持しません（ステートレス）。フロントが保持した確認済みデータを、Stage Bのリクエストで受け取ります。

### プロンプトを分離する

```text
features/ai_analysis/prompts/
├── stage_a.py
└── stage_b.py
```

巨大な文字列をrouterやclientへ直接書きません。

### OpenRouter接続を分離する

```text
features/ai_analysis/clients/openrouter.py
```

AI接続処理とプロンプト作成・分析ロジックを分けます。

**ZDR（Zero Data Retention）対応Endpointのみを利用する指定は、`clients/openrouter.py` の中で必ず行います。** 呼び出し側の判断に任せず、指定漏れが起きない形にします。

### AI出力を信用しすぎない

AIレスポンスは外部入力と同様に扱います。

- 必要な項目が存在するか確認する
- 想定した形式か確認する（schemaでの検証）
- 欠損・検証失敗時の処理（再試行の上限、エラーの返し方）を用意する
- AIの自己申告した「確実性」だけを正しさの根拠にしない
- Stage Aは小数点の誤読などが起こる前提とし、出力を自動確定しない（保護者の確認を必ず挟む）

### 「判定困難」を正常な結果として扱う

根拠不足時にAIへ無理な断定をさせません。

ただし、PRDでは次の状態は扱いが異なるため、**別の型として定義**し、混ぜません。

**単元の状態**（例）

```text
in_scope        MVP対象の単元
out_of_scope    MVP対象外の単元
undetermined    単元を特定できない（判定困難）
```

- `out_of_scope`：対象外であることを返して分析を終了する。履歴にもランキングにも含めない。
- `undetermined`：履歴に保存せず、ランキングにも含めない。

**原因の種類**（例）

```text
blank                        空欄
careless_mistake             ケアレスミス
insufficient_understanding   理解不足
undetermined                 判定困難
```

- 原因が `undetermined`（根拠不足）の場合は、**正常な結果として扱い、保存する**。
- 「理解不足」は誤判定のリスクが高いため、コメントの表現は断定を避ける（表現の方針はプロンプト側で管理する）。

いずれも実際のschema設計に合わせて命名・管理します。

## 14. AIモデル名・設定値

モデル名や共通設定を複数ファイルへ直接書かないようにします。

- モデル名（`OPENROUTER_MODEL`）やタイムアウトなどは、環境変数から `core/config.py` の設定クラス経由で読みます。
- 各ファイルから `os.getenv` や `os.environ` を直接呼びません。設定は `core/config.py` を通して取得します。

モデル変更時に多数のファイルを修正する構成を避けます。

---

## 15. プライバシー・テスト画像

テスト画像には児童名等が含まれる可能性があります。

- **画像は保存しない。** ディスク・DB・Memcachedに書かず、メモリ上で処理してStage A完了後に破棄する（一時ファイルが必要になった場合は、PRD「データ保存方針」の削除ルールに従う）
- ログへ画像内容（base64を含む）や個人情報を出さない
- ログへAIの入出力の全文を出さない（デバッグ時も同様）
- 個人名をデバッグ用固定データに使わない
- 実際のAPIキーをコードへ書かない
- 実テスト画像をリポジトリへコミットしない
- 検証データ・デモ用データの画像は、著作権フリーまたは利用許諾済みのものに限る（PRD「8. 著作権・データ保存方針」）
- 検証データを追加する場合は個人情報が含まれていないことを確認する

## 16. セキュリティ

### ユーザーの特定

- 学習履歴や利用回数は `user_id` に紐づきます。**`user_id` をリクエストのbodyやクエリから受け取りません。**
- ログイン中のユーザーは、Firebaseのトークンを検証する認証Dependency（`auth/dependencies.py`）から取得します。
- 認証が必要なAPIは、必ずこのDependencyを通します。

### Stripe Webhook

Webhookは、`STRIPE_WEBHOOK_SECRET` を使った**署名検証を必須**とします。署名を検証していないWebhookの内容は信用しません。

### CORS

CORSは、`FRONTEND_ORIGIN` で指定したオリジンのみを許可します。`*` は使いません。

### SQL・レスポンス

「DBアクセス」「Request / Response」のルールに従います（SQLの文字列連結の禁止、DBモデルの直接返却の禁止など）。

---

## 17. 環境変数・秘密情報

秘密情報は環境変数で管理します。

環境変数の一覧は、**`.env.example` を正**とします。この規約には一覧を載せません（二重管理を避けるため）。

禁止：

```python
OPENROUTER_API_KEY = "実際のAPIキー"
```

- `.env` の実値をGitへコミットしません。
- `.env.example` には変数名だけを記載します。
- Firebaseのサービスアカウントキーなどのファイルも、GitとDockerイメージに含めません（`.gitignore` / `.dockerignore` の対象）。
- 環境変数は `core/config.py` の設定クラス経由でのみ読みます。

---

## 18. エラーハンドリング

想定されるエラーを握りつぶしません。

避けたい例：

```python
try:
    ...
except:
    pass
```

必要な例外を明示します。

```python
try:
    ...
except SomeExpectedError as exc:
    ...
```

### 正常な結果とエラーを分ける

- **対象外の単元・判定困難は、エラーではなく正常な結果**として、レスポンスの状態で返します。
- エラーとして扱うのは、AI呼び出しの失敗・タイムアウト、認証エラー、利用回数の超過、レート制限などです。
- Frontendへ返すHTTPステータスと、Backend内部の例外を適切に分けます。

詳細な共通例外設計とHTTPステータスの対応表は、API設計時に確定します。

---

## 19. Logging

デバッグ目的で `print()` を大量に残さず、loggingを利用する方針とします。

ログに含めないもの：

- API Key
- Password
- Firebase token
- Stripe Secret
- 子どもの氏名
- テスト画像のデータ（base64を含む）
- AIの入出力の全文

ログは「障害原因を追えるが、秘密情報は残らない」ことを基準にします。

---

## 20. import

並び順は **Ruffの整列ルール（`I`）に任せます**。手作業で並べたり、区分けのコメントを付けたりしません。

```python
import os

from fastapi import APIRouter

from app.features.ai_analysis.service import analyze_test
```

- 標準ライブラリ、外部ライブラリ、自分のコードの順に、Ruffが整列します。
- 他featureのimportは、「feature間の依存の向き」に従います。
- 不要なimportは残しません。

---

## 21. コメント・docstring

コードをそのまま日本語へ翻訳するだけのコメントは不要です。

避けたい例：

```python
# userを取得する
user = get_user()
```

「なぜその処理が必要なのか」がコードだけでは分からない場合にコメントします。

```python
# Stage Bには保護者確認後のデータのみ渡す
confirmed_data = ...
```

複雑な関数・外部仕様に依存する処理には必要に応じてdocstringを付けます。

---

## 22. 共通化のルール

最初から `shared/` や `utils/` に何でも入れません。

原則：

1.  まずfeature内に実装
2.  別featureでも同じ処理が必要になる
3.  本当に共通化すべきか確認
4.  `shared/` 等へ移動

これにより、共通ファイルを同時に触る状況を減らします。

---

## 23. 依存ライブラリ

新しいライブラリを追加する場合は、もう一人のBackend担当へ共有します。

理由：

- `requirements.txt` / `pyproject.toml` 等が競合しやすい
- 同じ目的の別ライブラリが重複する可能性がある
- セキュリティ・保守性への影響がある

追加するときは、`requirements.txt` にバージョンを固定（`==`）し、追加する理由をPRに書きます。

「便利そう」という理由だけで依存を増やしません。

## 24. Formatter / Linter

BackendのFormatter / Linterには **Ruff** を採用します。

チーム共通の運用として、次を使用します。

- Formatter / Linter：Ruff
- VS Code：Ruff拡張機能を使用する
- 保存時自動整形：ONにする

コードスタイルはPEP 8を基本とし、Ruffによる自動整形結果を優先します。

### 有効にするルール（案）

```toml
[lint]
select = ["E", "F", "I", "UP", "B"]
```

- `E` / `F`：基本的な文法・未使用importなどの検出（`except:` の握りつぶしも検出される）
- `I`：importの整列
- `UP`：新しい書き方への更新
- `B`：バグになりやすい書き方の検出

> `B` を有効にすると、FastAPIの `Depends()` をデフォルト引数に書く形が警告されます。「APIルーター」の例のとおり、`Annotated[..., Depends(...)]` の形で書いてください。

Ruffの設定ファイル、実行コマンド、PR前に実行するチェックなどの具体的な設定は、Backend環境構築Issueで整備し、チーム全員が同じ設定を使用できる状態にします。

VS Codeの個人設定だけに依存せず、リポジトリ側で共有できる設定はチーム共通設定として管理します。

## 25. テストコード

テストは機能ごとに分けます。

```text
tests/
├── auth/
├── test_analysis/
├── ai_analysis/
├── learning_history/
├── usage/
└── payment/
```

テスト関数は、何を確認しているか分かる名前にします。

```python
def test_create_analysis_returns_success():
    ...
```

- テストフレームワークはpytestを使用します（#85）。既存のunittest形式のテストもpytestで実行します。実行手順はBackend READMEを参照してください。
- featureはフォルダ名を含むパスで識別します（例：`tests/test_analysis/test_stage_b_router.py`）。既存テストは改名せず、ファイル名には確認対象や役割が分かる名前を使います。別のfeatureに同名のテストファイル（`test_router.py` など）があるとpytestが衝突することがあるため、同名ファイルは作りません（#39）。
- **OpenRouter、Stripe、Firebaseは、テストではモックします。** 実際のAPI・本物のキーは使いません（費用・個人情報の面で危険なため）。

AIについては、通常の単体テストだけで「精度」を保証したことにしません。
Stage A / Stage Bの代表ケースによるPoC・回帰確認も別途継続します。

## 26. Gitコンフリクトを減らすルール

特に競合しやすいファイル：

```text
app/main.py
app/api/router.py
app/core/config.py
app/db/（session.py、models/__init__.py など。個別のテーブルファイル自体は features 単位で分かれているため、同時編集の対象になりにくい）
requirements.txt
pyproject.toml
.env.example
Dockerfile
```

これらを変更する場合は、もう一人のBackend担当へ共有します。

原則として、担当機能の `app/features/<feature>/` 内で実装を完結させ、
**2人が共通ファイルを同時に編集する状況をできるだけ避けます。**

担当feature外のファイルを変更する必要がある場合も、もう一人のBackend担当へ共有してから作業します。

### 不要な変更を混ぜない

1つのPRに、目的と無関係なformat変更・ファイル名変更・大規模な移動を混ぜません。

例：

AI機能の修正PRで、関係のないpaymentコードを整形しない。

## 27. Pull Requestで確認すること

PR作成前に最低限確認します。

- [ ] 担当Issueの範囲だけを変更している
- [ ] APIキー・秘密情報を含んでいない
- [ ] 実テスト画像・個人情報を含んでいない
- [ ] 画像・AIの入出力全文・個人情報をログに出していない
- [ ] 型ヒントを付けている
- [ ] routerに複雑な処理を書いていない
- [ ] DB処理が適切な層に分離されている
- [ ] feature間の依存の向きを守っている
- [ ] `user_id` をリクエストから受け取らず、認証Dependencyから取得している
- [ ] Stage A / Stage Bの責務を混ぜていない
- [ ] `async def` の中で同期処理を呼んでいない
- [ ] テストを追加・更新した
- [ ] 不要な `print()` が残っていない
- [ ] 不要なimportがない
- [ ] Ruffのチェック・自動整形で問題がない
- [ ] 関係のないファイルを変更していない
- [ ] 新しい環境変数を追加した場合 `.env.example` を更新した
- [ ] DBを変更した場合、ER図も更新した
- [ ] READMEやAPI仕様への影響がある場合、関連ドキュメントも更新した

## 28. レビュー時の考え方

レビューでは「自分ならこう書く」という好みだけで変更を求めず、次を優先します。

1.  バグ・セキュリティ
2.  仕様との不一致
3.  責務分離
4.  可読性
5.  テスト
6.  チーム規約
7.  個人的な書き方の好み

大きな設計変更が必要な場合は、レビューコメントだけで進めずチームで共有します。

## 29. 禁止・避けるパターンまとめ

```text
× main.pyにすべてを書く
× 1つのroutes.pyに全APIを書く
× routerから直接SQLを書く
× routerから直接OpenRouterを呼ぶ
× Stage AとStage Bを1つのプロンプトに混ぜる
× Stage Bに画像を渡す
× AIの生レスポンスを無検証でFrontendへ返す
× user_idをリクエストのbodyやクエリから受け取る
× SQLを文字列連結（f-stringなど）で組み立てる
× DBモデル（table=True）をそのままResponseで返す
× async defの中で同期処理（Stripe・pymemcache・DBなど）を呼ぶ
× 画像をディスク・DB・Memcachedに保存する
× 画像やAIの入出力全文をログに出す
× APIキーをコードへ書く
× 実テスト画像をGitへ入れる
× テストで実際のAPI・本物のキーを使う
× except: pass
× 共通化目的で巨大なutils.pyを作る
× Issueと無関係な変更をPRへ混ぜる
```
