# 技術選定

## 更新履歴

### 2026/09/19 更新

- 決済機能：🔵検証中 → 🟢決定（Stripe）。テストモードが無料・審査不要で卒業制作のデモに適していること、FastAPIとの連携実績が豊富なこと、課題要件でも例示されている標準的な選択肢であることが決め手。比較したPAY.JP／KOMOJU／Square／Epsilonは、月額費用の発生（Epsilon）や用途のズレ（Square）等から不採用
- キャッシュサーバー：🔵検証中 → 🟢決定（Memcached）。MUST要件への対応が主目的であり、Redisの多機能さを活かしきれず「なぜRedisにしたのか」を説明しにくくなるため、シンプルなMemcachedを採用。カウンター機能（incr/decr）で課金ポイント（○回以上の利用は有料）を実装する方針

- リスクと対応：Redis／Memcachedの行を更新し、Memcached採用に伴う実装上の注意点（既製のレート制限ライブラリが少なく、自前実装が必要）を追記

## 1. 選定方針

**「AI画像解析を中心としたMVPを約3週間で実装すること」を最優先に考えた。**

本サービスの核となる機能は、AI（Vision対応LLM）による解答画像の分析である。この核心機能と親和性の高い技術構成を優先しつつ、フロントエンドとの連携のしやすさ、実装期間（実質3週間）という制約の中で確実に完成させられることを重視して選定した。学習コスト・運用コストよりも、「核となる機能を確実に動かせるか」を優先度の一番上に置いている。

## 3. 比較サマリ

- **バックエンド**：FastAPI（Python）を採用。NestJS／Express（Node.js系）はフロントエンドとのTypeScript統一という利点はあったが、AIライブラリ・画像処理ライブラリの充実度でPython系に劣ると判断し不採用。Django（Python）はエンタープライズ規模のWebアプリケーションに強みがあり、MVP開発には機能過剰と判断し不採用。Laravel（PHP）はフロントと言語が分かれる上、新たな学習コストが発生するため不採用。Spring Boot（Java）は学習コストが高く、初学者チームには時間的に厳しいと判断し不採用。Ruby on Railsは「MVP開発に向く」という特徴は魅力的だったが、Node.js系と比べて情報量・チームの学習リソースとの相性が未検証だったため不採用。
- **プログラミング言語**：フロントエンド（TypeScript）とバックエンド（Python）で言語を統一せず、あえて使い分けた。理由は、核心機能であるAI画像解析との親和性を優先したため。両言語とも「型を明示し、実装時にデータの不整合を検知できる」という設計思想は共通しており、チーム開発における可読性・保守性は保てると判断した。
- **データベース**：PostgreSQLを採用。MySQLとの詳細な比較検証は行っておらず、拡張性・データ型の豊富さ・セキュリティ面の強さを踏まえて選定した（比較を省略した点は今後の検討事項として残る）。
- **ORM**：SQLModelを採用。Prisma／TypeORMはNode.js系フレームワーク向けのため、バックエンドをPython（FastAPI）にした時点で対象外となった。SQLAlchemy単体という選択肢もあったが、FastAPIとの統合のしやすさを優先しSQLModelを選んだ。

## 5. 処理フロー（Issue #11）

シーケンス図の代替説明とする（GitHub運用書 §11）。[アーキテクチャ設計](アーキテクチャ設計.md)と合わせて読む。既存の更新履歴は技術選定時の記録として残す。

### 認証とAI分析

1. FrontendはFirebase SDKで新規登録・ログイン・ログアウトを行い、認証状態を監視する。ログイン後はIDトークン付きで`PUT /v1/users/me`を呼び、アプリユーザーを初期登録する。分析・履歴APIもIDトークンを付け、401時はログアウトする。
2. 画像を選択し、必要なら氏名等を任意トリミングする。Stage A（`POST /v1/analyses`）で最大2枚のJPEG／PNGを検証し、月間利用可否と短時間レート制限を判定してからOpenRouterで事実を抽出する。画像は永続保存しない。
3. 保護者が読み取り内容を確認・修正し、得点・満点を入力する。Stage B（`POST /v1/analyses/{analysis_request_id}/result`）へ確認済みテキストだけを送る。
4. Stage B開始前にも月間利用可否と短時間レート制限を判定する。単元判定後、対象単元なら必要な誤答パターン分析とコメント生成を行う。
5. 完了結果の保存直前にユーザー単位のDBロックを取得し、保存済みIDと月間上限を再確認する。利用実績と分析記録を同一トランザクションで保存する。対象外・単元判定困難は保存・利用消費なし。

無料は月2回、有料は無料分を含め月10回（`MONTHLY_ANALYSIS_LIMIT`の既定値）。日本時間の暦月でDBの利用実績を数える。無料枠消費後にactive契約がなければ403 `PLAN_REQUIRED`、月間上限なら契約の有無にかかわらず403 `MONTHLY_LIMIT_REACHED`を返す。Frontendは`GET /v1/usage`の`can_analyze`と`blocked_reason`を使い、分析開始・有料案内・月間上限の表示を切り替える。

MemcachedはStage A／Stage Bを別々に1ユーザー1分3回まで制限する。分単位の固定窓とTTL 120秒のカウンターを使い、超過時は429と`Retry-After`を返す。接続不可・カウンター消失時は警告を出して分析を継続する。Stage A発行IDの所有者・期限検証とIdempotency-Keyによる再送制御は未実装。

AI通信はクライアント側でZDRとデータ収集拒否を必須指定し、Providerを`novita`／`io-net`に限定する。

### 決済

BackendとFrontendの決済フローは次のとおり。

1. 認証済みユーザーが`POST /v1/billing/checkout-sessions`を呼ぶと、ユーザー単位のDBロックを取得する。DBにあるactive契約をStripeで再確認し、有効な契約があれば409 `ALREADY_SUBSCRIBED`を返す。
2. 同じユーザーの古い未完了Checkoutを失効し、サーバー設定の月額価格・認証結果のユーザーIDで新しいCheckout URLを作成する。
3. `POST /v1/webhooks/stripe`で生の本文と署名を検証する。不正署名は400。対象イベントの重複を排除し、契約単位のロック下でStripeから最新状態を取得する。取得失敗はrollbackと503で再送に備える。
4. 二重active契約が発生した場合はユーザー単位で直列化し、後発を解約する。解約失敗は503で再送を待つ。テストモードのため返金は行わない。
5. イベント記録と契約状態を同じトランザクションで保存する。アプリユーザーに紐づかないイベントは契約を更新せず、処理済み記録だけを残す。`GET /v1/subscriptions/current`は保存済みの現在の契約状態を返す。成功URLの表示だけで有料状態を確定しない。
6. Frontendは認証付きでCheckout作成APIを呼び、`https://checkout.stripe.com`配下と確認できたURLだけを新しいタブで開く。成功時の戻り先では契約状態を直ちに取得し、1秒間隔・最大10回再取得して、`active`を確認した場合だけ成功表示にする。

実装根拠は`backend/app/features/test_analysis/service.py`、`usage/`、`payment/`、`frontend/lib/firebase/auth.ts`、`frontend/lib/api/client.ts`、`frontend/lib/api/usage.ts`、`frontend/features/plan/components/PlanGuide.tsx`。安全性と未対応事項は[セキュリティ設計](セキュリティ設計.md)を参照。
